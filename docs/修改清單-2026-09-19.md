### A3 — 換掉 `WEBHOOK_SECRET`（安全性問題，請完整讀）

目前 Vercel 上的 `WEBHOOK_SECRET` 實際值就是程式碼預設的 `abc123`，而 cron 打的
網址是 `…/api/analyze?secret=abc123`。

拿到這個 secret 能做的不只是燒 CPU 額度：

- `DELETE /api/analyze` 只要 webhook secret 就通過（`src/app/api/analyze/route.ts`
  的 DELETE handler）。不帶 symbol 會清掉 `tlock:*`、`circuit_breaker*`、
  `btc_pause:*`、`loss_cd:*`——**熔斷、止損後冷卻、BTC 暫停、訊號鎖全部解除**。
- 加 `?scope=drawdown` 還能解除回撤停機。

等於把所有風控開關放在一個猜得到的網址後面。此外 secret 放在 URL query string
裡，會留在 cron-job.org 的執行紀錄與任何中間節點的日誌。

**要做兩件事，缺一不可：**

1. Vercel 環境變數 `WEBHOOK_SECRET` 改成隨機長字串。
2. cron-job.org（job 7981693）改用**自訂 header** `x-webhook-secret` 傳遞，
   而不是 query string。`checkAuth` 是 header 優先（`x-webhook-secret` ?? query
   param），cron-job.org 的「進階」分頁可設自訂 header。

**順序：先設 Vercel 環境變數 → 等重新部署完成 → 再改 cron。** 反過來會讓 cron
在部署完成前就送新 secret，被舊環境擋成 401。

空窗期的後果只是少跑幾輪掃描（系統本來就有約一半的呼叫在撞鎖跳過），無資料損失。

> testnet 期間財務損失是 0，所以不急迫；**但真錢之前一定要換**。
> `scripts/live-runner.ts` 的 `--live` 硬擋是刻意保留的安全閥，這項完成前不要拆。

### B1 — Vercel CPU：定位那 2.16 秒 ✅ 2026-09-19 用使用者提供的 Vercel token 查完 log，缺口大幅縮小

用 `vercel logs` 拉了兩輪 production `[analyze][cpu]` 真實資料。第一輪
（部署前）wall 與 total 的缺口高達近 50%，讀 code 發現兩段從沒被計時的地方
（每 symbol 迴圈尾端 `await delay(300)` 的 rate-limit 睡眠、fundingRate 之後
到迴圈結尾整段 confluence/DB-insert/webpush），補上計時器（見
`src/app/api/analyze/route.ts` 的 `decisionWriteNotify`/`rateLimitDelay`
兩個新 stage，commit `7518b77`）後重新量測：

```
wall 17780ms | total 14461ms（缺口剩 3319ms，19%，主要是 pass 2 深處理與
setup 階段還沒包計時，比之前的近 50% 好很多）
rateLimitDelay      4502ms/15次  31.1%  ← 最大單項，比 regimeAtr 還大
regimeAtr           1744ms/15次  12.1%
fetch:4h(540)       1740ms/15次  12.0%
fetchHtf:1d         1633ms/14次  11.3%
fetch:1h            1443ms/15次  10.0%
monitorActiveTrades 1326ms/1次    9.2%
fundingRate         1127ms/15次   7.8%
processShadowTrades  475ms/1次    3.3%
decisionWriteNotify  406ms/15次   2.8%
signals（全部時框）    65ms/29次   0.4%  ← 原本推論的「訊號產生只佔0.4%」被證實
```

⚠ **`rateLimitDelay` 是 `setTimeout` 純睡眠，不是計算**——如果 Vercel 的
Fluid Active CPU 真的只算「CPU 忙碌」時間（不算 idle wait），這 31% 的
wall time 對「CPU 超標」這個原始問題可能完全不相關，砍掉只會縮短 wall
clock/降低撞 lock 的機率，不一定解決 Active CPU 108% 的帳單問題。同理
fetch:*／fundingRate／regimeAtr 這些如果本質是「等網路回應」而非「算
ADX/ATR 的 Wilder 遞迴本身」，也可能大部分不算 Active CPU——這份計時器
量的是 wall time，不是 CPU cycles，兩者在 I/O-bound 的程式碼裡會分岔。

**沒有動 `delay(300)` 這個值**——它是刻意的 Binance rate-limit 節流，附近
完全沒有註解說明抓 300ms 的理由，改動前要先查 Binance 實際 weight-based
rate limit 用量，砍太多有觸發 429/IP 封鎖的風險，這超出「量測」範圍、
需要使用者決定要不要排。

下一步（使用者決定要不要做）：去 Vercel Dashboard → Observability →
Functions，看 `/api/analyze` 的 Active CPU（不是 wall duration）逐次分佈，
才能真正回答「是不是這些 stage 在燒 CPU 帳單」，CLI 目前查不到那個粒度。

現況推導：

```
13 分鐘/日 ÷ 360 次完整掃描 ≈ 2.17 秒 CPU / 次
其中訊號產生 + K 線解析 ≈ 5 ms      ← 實測，佔 0.4%
剩下 2.16 秒不知道在哪
```

計時點已經鋪好（`src/lib/scanTiming.ts` + `route.ts` 的五個階段），
部署後 log 會印一行 `[analyze][cpu] wall ...ms | ...`。候選：
`monitorActiveTrades`（每筆持倉抓 168 根 K 線 + `walkTpSl`）、
`processShadowTrades`（三個影子模擬）、`regimeAtr`（540 根 4h + ADX + ATR 百分位）、
`fundingRate`、Supabase 讀寫。

**本機量不到**——沒有 Supabase 時 `monitored: 0`，監控階段是空跑。

`scan-run-lock` TTL 70 → 240 秒已改（`ceb79c2`，已上線），預期直接 ×0.5。
下一個計費週期驗收：Vercel CPU < 60%。

### B2 — 心跳改寫 Supabase（交接判斷不再依賴 Redis）✅ 已完成（早於本清單）

**這份清單寫錯了現況。** 查 git log 發現 `decideLiveRunnerHandoff`
（`src/lib/liveRunnerHandoff.ts`）與 route.ts/live-runner.ts 的雙來源交接判斷
早在 `9d3acfb`（2026-08-26）就已實作並合併進 main，比這份清單的寫成日期
（2026-09-19）早了三週多。純函數 27 個測試全過，route.ts 已 import 使用。
下面原始描述保留供追溯，但**不用再做**。

⚠ 順手發現一個清單沒列到的缺口：`route.ts`/`live-runner.ts` 的 Supabase
寫入/讀取都指向 `profiles.live_runner_heartbeat_at`，程式碼裡兩處都印了
「欄位不存在」的警告訊息與對應的 `ALTER TABLE` 建議——**這個欄位沒有出現在
上面 A6 的 migration 清單裡**。若還沒手動加過，請一併執行：

```sql
ALTER TABLE profiles ADD COLUMN IF NOT EXISTS live_runner_heartbeat_at BIGINT;
```

沒加不會壞（有 fallback），但 Redis 掛掉時交接判斷會退回舊的「假設活著」行為，
等於 B2 想補的洞沒有真的補上。

**這是目前最大的靜默失效缺口。** 兩個各自合理的保守設計疊起來造成全面空窗：

- `route.ts` 心跳檢查的 catch 分支：Redis 查詢失敗時**假設 live-runner 還活著**，
  把該使用者的單整批排除、不接手。
- live-runner：Redis 掛掉時繼續監控（`f0c51f9` 已修）。

已修的一半是 live-runner。**還沒補的一半**：live-runner 真的停了（EC2 關機）
**而且** Redis 也掛了 → route.ts 仍假設它活著 → 沒人監控、沒有任何警告。
這就是 8/23–8/26「TP1 打到卻沒平 50%」的完整解釋。

**修法**：心跳雙寫 Supabase，交接判斷讀 Supabase。跟 `240352a` 修 -4141 迴圈
同一個理由——把關鍵狀態放在當下真的活著的儲存上。

> 通則：兩個元件都 fail-safe 到「對方會處理」時，兩邊同時壞掉就是靜默的全面
> 失效。任何「交接」設計都要有一方能偵測到「沒有人在做」。

## 五、為什麼改策略這件事本身要小心

使用者的三個判斷依據裡，**第 2 點需要修正**：現有系統已經是 SMC——
`analyzeMarketStructure`（BOS/CHoCH）、Order Block、breaker block、HTF bias、
盤整不發單、保本、分批停利全都在裡面。真正缺的只有四項：
**流動性掃描、FVG、溢價/折扣區、D1 偏向**。

虧損是算術，不是規則寫錯：

```
賺賠比 2.2:1、勝率 27.5%
EV = 0.275 × 2.2 − 0.725 × 1 = −0.12R      實測 −0.081 ~ −0.107R，對得上
2.2:1 的兩平勝率 = 1/(1+2.2) = 31.3%        差 3.8 個百分點
手續費 −94.60 USDT ÷ 90 天淨虧 −469.69 = 20%
```

修正 EV 只有兩條路（推遠 TP、拉近 SL），**兩條都已測死**。第三條沒測過的是
**改「在哪裡進場」**——五輪測試的共同盲點是全部在「同一個進場點上調參數」。
這就是 B3/B4 要做的事。

### 無法迴避的限制，寫在這裡防止誤讀

sd ≈ 1.3，偵測 +0.1R/筆需 **n ≈ 665**，以每天 1.9 筆計約**一年**。

**「帳戶曲線轉正」這個目標，在本清單全部做完之後仍然無法被證明或證偽。**
這不是保守，是 n 與 sd 算出來的。任何「改完之後曲線轉正」的觀察，在 n 夠大之前
都無法跟運氣區分。
