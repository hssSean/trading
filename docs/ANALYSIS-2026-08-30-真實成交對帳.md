# 2026-08-30 真實成交對帳：第一組可信的績效數字，以及量測系統的系統性偏誤

> 承接 `ANALYSIS-2026-08-25-三層量測全部無鑑別力.md`。那份用模擬證明三層都
> 測不出可調的槓桿；這份用**幣安真實成交紀錄**獨立確認了同一件事，並且發現
> 過去所有績效數字都建立在被污染的資料上。
>
> **調參前先讀這份。** 尤其是第四節那個我自己差點掉進去的選擇偏誤陷阱。

## TL;DR

| 項目 | 結果 |
|---|---|
| 真倉 73 筆對帳 | OK 49、硬證據捏造 10、軟證據 14 |
| **真實績效（n=69）** | **每筆 −0.107R，合計 −7.36R，t=−0.69** |
| 勝率 | 27.5%（19/69） |
| **DB 模擬 vs 真實** | **DB 低估 67.6%，符號檢定 z=2.91 顯著** |

**兩個結論：**

1. **策略有沒有邊際，這批資料仍然回答不了**（t=−0.69）。跟 8/25 三層模擬的
   結論一致，但這次是真實成交，不是模擬。
2. **量測系統本身有統計顯著的偏誤**（z=2.91）——DB 模擬系統性地把結果記得比
   實際差。這是整輪調查唯一顯著的發現。

---

## 一、捏造出場的機制：`-0.05%` 是簽名

7 筆 SIGN_FLIP 的 DB 值**全部剛好是 `-0.05%`**。追到源頭：

```ts
// src/lib/monitorMath.ts:44
export const STOP_EXIT_SLIPPAGE_PCT = 0.0005; // 0.05%，對交易者不利的方向
```

`-0.05%` = 保本價（= 進場價）扣掉滑價。**那些全是 DB 模擬捏造的「保本出場」。**

機制（`6e357a3` 已修）：`/api/analyze` 的 DB 模擬用 **K 線收盤價**推演，幣安用
**標記價**觸發。一根影線碰到保本價，模擬就判「出場」寫進 DB；真實倉位還開著，
繼續往上跑。

### 為什麼這個 bug 特別惡性

保本止損**只有在單子已經進入獲利之後才存在**（TP1 後，或 pre-TP1 +0.8R 那道）。
所以這個 bug 結構上**只能砍掉當時正在賺錢的單**：

```
XRP  DB -0.06%  實際 +3.79%   +4.644R
SOL  DB -0.05%  實際 +4.00%   +4.089R
ETH  DB -1.16%  實際 +2.56%   +2.309R
BNB  DB -0.05%  實際 +1.66%   +1.643R
BTC  DB -0.05%  實際 +1.59%   +1.577R
ENA  DB -0.05%  實際 +4.20%   +1.000R
ZEC  DB -0.05%  實際 +6.01%   +0.744R
```

**約 +16R 的真實獲利被記成 0 附近。** 這解釋了 8/29 的回撤停機——DB 眼中憑空
少了 16R，越過 12R 上限，系統把自己停掉。

## 二、抓取上限：靜默低報 110 USDT

`userTrades` 單次上限 1000 筆。原本只用 7 天時間窗查，HYPEUSDT 七天內有 1012
筆成交，超出的被靜默丟掉。改用 `fromId` 續抓後（同一批 69 筆單，只改抓取方式）：

```
已實現損益   -173.19  →  -283.97 USDT
每筆 R        -0.082  →   -0.107R
合計 R         -5.69R →    -7.36R
```

漏掉的成交不只讓總額失真，還會讓正常平倉被判成 `NO_CLOSE_FILL`——硬證據等級的
誤判，會導致去「修正」本來就對的紀錄。

> **通則：任何有分頁上限的 API，「剛好拿滿一頁」就要當成「可能還有」。**

## 三、真實績效

```
                        n     每筆      合計      sd     t
全部                    69   -0.107R   -7.36R   1.29  -0.69
排除 ZEC/HYPE（配對最差） 55   -0.128R   -7.02R   1.32  -0.72
勝率 27.5%（19/69）
```

`|t| < 2` 代表**這批資料分不出「平均 R ≠ 0」**，不等於沒有邊際，也不等於有。

### 檢定力邊界

sd = 1.29。要偵測到真實邊際：

| 想偵測的效果 | 需要的 n | 以每天 1.9 筆計 |
|---|---|---|
| +0.1R/筆 | ~665 | 約 1 年 |
| +0.3R/筆 | ~74 | 約 5 週 |

n=69 只能看見 `|mean R| > 0.31R` 的效果。**所以「9 月底驗證策略可獲利」在數學上
不可能**——不是保守，是 n 和 sd 算出來的。

## 四、⚠ 我差點掉進去的選擇偏誤

報告裡有這一行，看起來是整份最強的證據：

```
只看判定 OK 的    n=49   每筆 -0.367R   t=-2.75   ← 顯著
```

**這個數字不能用。** 「OK」= DB 跟現實一致；而被排除的 SIGN_FLIP **絕大多數是
贏家**（真實獲利被記成 −0.05%）。把贏家篩掉之後剩下的當然偏虧。

`t=-2.75` 是篩選造出來的，不是策略的性質。

> **通則：任何「只看資料品質好的那部分」的子集分析，先問「品質差的那部分是不是
> 系統性地偏向某個結果」。** 這裡答案是「是，而且偏得很嚴重」。

保留這一行在報告裡是刻意的——它會一直長得像顯著結果，寫在這裡讓下一個看到的人
（包括未來的我）不要重蹈。

## 五、DB 模擬的系統性偏誤（唯一顯著的發現）

```
真實 − DB 模擬 = 0.362 個百分點/筆   t=1.91   （不顯著）
DB 低估結果的比例 67.6%（46/68）      z=2.91   ← 顯著
```

兩種檢定不一致，而**那個不一致本身就是資訊**：

- **t 檢定**用到幅度，被幾筆 +4R 的捏造出場（厚尾）稀釋掉檢定力
- **符號檢定**只數正負，對厚尾免疫

偏誤如果是「方向一致但幅度不定」，t 會看不到而符號檢定看得到——那正是系統性
偏誤的典型形狀。

### 為什麼這件事比它看起來更嚴重

同一批已結束交易裡，**76 筆是純 DB 模擬**（沒有 `exchange_entry_order_id`，
從未送到交易所）。它們**永遠無法對帳**，但跟真倉共用同一套推演邏輯。

所以在真倉上量到的偏誤，就是對那 76 筆誤差的最好估計——**所有建立在模擬資料上
的歷史統計都偏悲觀**，包括影子模擬的基準線。

## 五之補（2026-09-01）：軟證據判讀完畢，結論不變

樣本長到 78 筆後重跑。**兩個檢定現在都顯著**（8/30 時 t 檢定還差一點）：

```
真實 − DB 模擬 = 0.420 個百分點/筆   t=2.23   ← 顯著
DB 低估結果的比例 68.4%（52/76）      z=3.21   ← 顯著
```

### 12 筆軟證據的分類

軟證據（`AMOUNT_MISMATCH` / `PARTIAL_CLOSE`）麻煩的地方在於：DB 跟現實對不上，
但**對不上不代表 `realR` 錯**——`realR` 來自交易所成交紀錄，DB 錯不影響它。

真正會讓 `realR` 失真的只有一件事：**FIFO 把別筆單的平倉成交配給了這筆**。
所以分類的關鍵不是「差多少」，是「這個 symbol 的成交密度高不高」：

```
捏造保本出場的殘留（DB 記 -0.05%）   3 筆   -2.41R   → realR 可信（錯的是 DB）
高成交密度，FIFO 可能誤配            2 筆   -2.01R   → realR 存疑
一般滑價/部分成交誤差                7 筆   +0.04R   → realR 可信
```

那 3 筆 `-0.05%` 是同一個保本捏造 bug 的殘留，只是它們的真實結果後來是虧的，
所以沒被判成 `SIGN_FLIP`。

**78 筆裡只有 2 筆的 `realR` 有疑慮，合計 −2.01R。** 排除後：

```
全部           n=78   -0.081R   t=-0.55
排除 ZEC/HYPE  n=62   -0.083R   t=-0.49
```

**結論完全不變。** 對帳這條線到此收尾——資料品質的問題已經量化完畢，剩下的
不確定性小到不影響任何判斷。

## 六、接下來

**不要做**：調整任何評分權重、出場參數、掛單距離。兩個獨立理由——三層模擬測不出
效果（8/25），真實成交也測不出（本份）；而且你現在才知道過去資料是髒的，用髒
資料調參，錯的方式無法預測。

**要做**：

1. **跑 migration 並標記髒資料**（`npm run audit-exits` → `apply-audit-marks.ts --apply`）

   ```sql
   ALTER TABLE trades
     ADD COLUMN IF NOT EXISTS audit_verdict TEXT,
     ADD COLUMN IF NOT EXISTS audit_real_pnl_usdt DOUBLE PRECISION,
     ADD COLUMN IF NOT EXISTS audit_real_r DOUBLE PRECISION,
     ADD COLUMN IF NOT EXISTS audit_at BIGINT;
   ```

   統計排除髒資料時過濾 `audit_verdict NOT IN ('NO_CLOSE_FILL','SIGN_FLIP')`。
   **原始的 `result` / `pnl_percent` / `exit_price` 刻意不改**——那些記錄的是
   「當時系統以為發生什麼」，是除錯證據，我們正是靠這個對照才定位到 bug。

2. **定期重跑對帳**。捏造出場的 bug 已修，但下一個類似的 bug 只有對帳看得出來。

3. **累積乾淨樣本**。`6e357a3` 之後的資料是乾淨的，那才是真正的樣本外驗證集。
