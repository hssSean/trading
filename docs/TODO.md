## 🔴 交接判斷只靠 Redis——兩邊同時壞掉時沒有任何東西在監控持倉

**2026-08-26 查到，這是 8/23–8/26 那次「TP1 打到卻沒平 50%」的完整解釋。**

兩個各自都合理的保守設計疊在一起，造成全面空窗：

- **route.ts**（`route.ts` 心跳檢查的 catch 分支）：Redis 查詢失敗時**假設
  live-runner 還活著**，把該使用者的單整批排除、不接手。單獨看是對的——
  避免兩邊搶著處理同一批單。
- **live-runner**：`getKillSwitchState` 是裸的 `redis.get`，排在 `runCycle`
  所有監控邏輯**之前**且沒有 try/catch。Redis 一掛，每輪都在監控開始前中斷。
  （已於 `f0c51f9` 修掉）

疊起來：Redis 額度用盡 → live-runner 每 15 秒失敗一次、沒掛任何 TP1 條件單
也沒移動止損；route.ts 以為它還活著、不接手 → **沒有任何東西在管持倉，
而且沒有任何錯誤或警告**。

TP1 是**預掛在交易所**的 `TAKE_PROFIT_MARKET` + reduceOnly + 50% 數量，
觸價由交易所執行。空窗期新開的單根本沒掛上那張單，所以價格穿過 TP1 也不會
有動作。硬止損不受影響（是 resting order）。

**已修的一半**：live-runner 現在 Redis 掛掉也會繼續監控。

**還沒補的一半**：如果 live-runner 真的停了（EC2 關機）**而且** Redis 也掛了，
route.ts 仍然假設它活著 → 一樣沒人監控、一樣無聲。

**修法**：心跳改寫進 Supabase（或雙寫），交接判斷就不依賴 Redis。跟 `240352a`
修 -4141 迴圈同一個理由——把關鍵狀態放在當下真的活著的儲存上。

> **通則**：兩個元件都 fail-safe 到「對方會處理」時，兩邊同時壞掉就是靜默的
> 全面失效。任何「交接」設計都要有一方能偵測到「沒有人在做」。

### ⚠ 推翻先前的假設：Redis 死掉讓 CPU 變高，不是變低

8/23 正是 Upstash 額度燒完那天。排除的候選：

### ✅ 機制已確認：`scan-run-lock` 才是真正的節流器

`route.ts:2236` 設 `scan-run-lock`，`ex: 70`，**全檔沒有任何 `del`**——鎖不會
被釋放，靠 TTL 自然過期。而外部 cron（cron-job.org，job 7981693）是
**每 1 分鐘**一次，不是文件寫的 5 分鐘：

```
cron 每 60 秒，鎖 TTL 70 秒
t=0    取得鎖 → 完整掃描
t=60   鎖還在（剩 10 秒）→ skip，~0 CPU
t=120  鎖過期 → 完整掃描
       ≈ 50% 的呼叫做完整工作
```

**Redis 死 → 鎖完全失效 → 100% 都做完整工作 → 正好 2×。** 精確對應觀測到的
翻倍，不是「差不多」。

推論：**實際掃描節奏一直是由鎖的 TTL（70 秒）決定，不是由 cron 間隔決定。**
`route.ts:2230` 的註解「the normal 5-min cadence is unaffected」已經過時。

### ⚠ webhook secret 是預設值 `abc123`

cron 打的網址是 `…/api/analyze?secret=abc123`，而 `abc123` 是程式碼裡的預設
fallback。等於這個端點實質上沒有保護——任何知道網址的人都能無限觸發掃描，
直接燒 CPU 額度（denial of wallet）。而且它在 URL query string 裡，會被中間
節點記錄。跟本次超標**沒有證據**相關，但無論如何都該換掉。

### 決定性的算術

```
現在日均 13 分鐘  × 30 = 6.5 h/月 = 162% 額度
8/23 前的 7 分鐘  × 30 = 3.5 h/月 =  87% 額度   ← 連「好的時候」都只剩 13% 餘裕
```

實際節奏是 60–70 秒一輪（見下方機制），改成 5 分鐘 ≈ **5 倍**降幅：

```
現在 13 min/day               → 6.5h/月 = 162%
cron 改 5 分鐘（÷5）  2.6 min/day → 1.3h/月 =  33%   安全
cron 改 7 分鐘（÷7）  1.9 min/day → 0.9h/月 =  24%   更安全
```

**結論：把 cron-job.org 的間隔從 1 分鐘改成 5 分鐘**（回到 `ARCHITECTURE.md`
記載的原始設計）。不是策略變更——監控用 `last_monitored_at` 回放 K 線，跟
間隔無關；真倉由 live-runner 每 15 秒管，不受影響。

改 cron 比改鎖的 TTL 好：**Redis 死掉時鎖完全失效，但 cron 間隔永遠有效**。

**不要同時動幣種數或 5m 時框**——9/1 Redis 回來已經是一個變因，再加一個就
分不出誰有效。**9/3 回來看，累計應 ≤ 24 分鐘。**

**8/26 已做的兩個修正**（都不動策略邏輯，效果被 8/23 的翻倍蓋過）：
- 掃描前剔除「幣安端下不了單」的 symbol（`240352a`）。省約 1/15。
- 悲觀影子軌跡改成預設關閉。每筆影子單少跑一次 walkTpSl（96-168 根 K 線）。

**檢查方式**：Vercel → 專案 → Usage → Fluid Active CPU。額度 4 小時 / 30 天，
線性換算：

| 到第幾天 | 應該不超過 | 超過就動手 |
|---|---|---|
| 3 天（8/30） | 24 分鐘 | **30 分鐘** |

### ~~B. `MAX_TOTAL_RISK_PCT=5` 在 live-runner 真倉路徑可能不是死碼~~ ✅ 2026-08-20 確認並修好

**2026-08-20 確認：不只不是死碼，它讓真倉零下單卡死了一整天。** 使用者回報
「一整天沒收到推薦單、模擬帳戶也沒下單」，查出來是這個。live-runner log：

```
HYPEUSDT [skip_entry] 全局風險上限：目前已開 4   + 這筆 1.5 = 5.5 會超過上限 5
BNBUSDT  [skip_entry] 全局風險上限：目前已開 4   + 這筆 1.5 = 5.5 會超過上限 5
ZECUSDT  [skip_entry] 全局風險上限：目前已開 4   + 這筆 1.5 = 5.5 會超過上限 5
ETHUSDT  [skip_entry] 全局風險上限：目前已開 4.5 + 這筆 1   = 5.5 會超過上限 5
```

四張 waiting 單（HYPE/BNB/ZEC 各 1.5、ETH 1.0）總和 5.5 > 5，每張算自己的
時候都是「其他三張＋自己＝5.5」→ 全部 skip_entry → 沒送出就不會成交、不會
平倉 → 5.5 永遠降不下來。**跟同日早上那個回撤停機完全同一種死結形狀**：
關卡擋住的東西正是解除關卡所需要的條件。

根因是把「推薦單」當成「持倉」：`totalOpenRiskPct` 加總了所有 `closed_at IS
NULL` 的列，包含從沒送出過訂單的。沒送出的單在交易所端沒有訂單、沒佔保證金、
沒有任何曝險，不該吃風險額度。

修法：抽出純函數 `calcTotalOpenRisk`（tradeBridge.ts），只加總
`exchange_entry_order_id !== null` 的列——已掛單的**要**算（限價單在幣安端
已佔住保證金，成交就是真部位），沒送出的不算。同時修掉呼叫端那個
`totalOpenRiskPct - 自己` 的減法（自己本來就不在總和裡，再減會少算、把上限
放寬）。`tests/engine/calcTotalOpenRisk.test.ts` 把上面那組實測數字原樣寫成
回歸測試。

**額度上限 5 本身沒動**——這次修的是「誰該計入額度」，不是放寬風控。

## 必做的安全控制

### 逐倉（ISOLATED）— 最關鍵
```
POST /fapi/v1/marginType {symbol, marginType: "ISOLATED"}
```
Binance **預設全倉**，全倉下單一部位虧損可吃掉整個帳戶。
逐倉把最壞情況從「帳戶歸零」降級成「賠掉那張的保證金」。

symbol 層級持久設定，有持倉時改不了 → 下第一張單前設好，每次下單前檢查。

### API key 權限
只勾 **Enable Futures**，**絕不勾提現**。

### 五層防護
1. **交易所層** — 逐倉、止損用 `closePosition=true` 的 `STOP_MARKET`、成交後立刻送
2. **下單前置檢查**（純函數 + 測試）— 強平緩衝 ≥3×、總保證金 ≤50%、精度/最小名目、
   權益硬地板、kill switch 未啟動、當日虧損未達上限
3. **watchdog**（獨立程序，不可跟下單引擎同一個會被殺的函式）— 每 30 秒對帳
   持倉 vs 掛單，「有持倉沒止損」立刻補單或市價平掉
4. **kill switch** — Redis flag 擋新單 + 一鍵撤單平倉；自動觸發條件（連續 API 錯誤、
   權益跌破地板、watchdog 連續偵測不一致）
5. **熔斷器接到下單層** — 現有熔斷器只擋訊號產生，要讓它也擋下單

## 技術清單

**簽名**：`HMAC-SHA256(queryString, secretKey)` 當 `signature`，header `X-MBX-APIKEY`，
每請求帶 `timestamp` + `recvWindow`。

**端點**：`POST /fapi/v1/leverage`（槓桿）、`POST /fapi/v1/marginType`（逐倉）、
`GET /fapi/v2/balance`、`GET /fapi/v2/positionRisk`、`GET /fapi/v1/openOrders`、
`POST`/`DELETE /fapi/v1/order`、`GET /fapi/v1/exchangeInfo`（公開）

**精度處理**（沒做會吃 `-1111` / `-4164`）：
```
LOT_SIZE.stepSize     → quantity 無條件捨去到整數倍
PRICE_FILTER.tickSize → price 必須是整數倍
MIN_NOTIONAL.notional → quantity × price ≥ 5 USDT
```

**冪等性**：`newClientOrderId = ${tradeId}-entry / -sl / -tp`。
重複送同 ID 會被拒（`-4015`）——這正是要的，cron 重跑不會重複開倉。

## 掛單過期功能會怎樣

**會保留，而且更可靠**，但機制反轉：

- **逾期 4 根 K 線** → 可以丟給交易所做（`timeInForce: GTD` + `goodTillDate`）。
  好處：系統掛掉訂單也會自己過期。（`goodTillDate` 有最小提前量限制，testnet 要實測）
- **結構突破 / 行情走遠 / TP1直達** → 動態條件，必須留在程式裡

**兩個現在完全沒有模型的新狀態**：

1. **部分成交** — 現在 `isFilled` 是 boolean，真實限價單可以只成交 30%。
   在部分成交後送取消 → 取消的是未成交部分，**已成交部分是真實持倉，需要止損不是取消**。
   判斷：讀 `executedQty`，>0 就走成交路徑補止損。

2. **取消 vs 成交競態** — 決定取消 → DELETE 在路上 → 訂單剛好成交。
   Binance 回 `-2011 Unknown order sent`。**不能當成取消成功**，必須重查 `positionRisk`。

**取消不要再刪 DB 列** — 現在是 `.delete()`，接真錢後要保留紀錄改 `status='cancelled'`，
否則對帳時發現交易所有一筆 DB 沒有的成交會完全追不到。

## 接上真錢後 monitor 會大幅簡化

現在的 Phase 1/2 是**掃 K 線猜**成交了沒、止損碰了沒。接交易所後不用猜——直接問。

**今天修的那一整類 bug 會消失**（幽靈成交、NULL status 沒人監控、客戶端覆寫伺服器），
因為交易所變成唯一真相來源，DB 只是鏡像。

代價：那幾百行 K 線掃描要重寫成「對帳」；成交判斷那段整段不需要，
但取消條件（看收盤價）還是要掃 K 線 → 迴圈會拆成兩半。
