## 〇、結論先講

**不是推播機制壞掉，是 live-runner 的通知分派函式只認得 3 種事件，其餘全部
靜默略過。**

昨天（8/12）修的是「VAPID 金鑰沒設定 → 一則都發不出去」，那是**傳輸層**。
這次是**分派層**：金鑰現在正常了，能發的都有發，但有 4 種事件根本沒有走到
發送這一步。

兩者是完全獨立的兩個 bug，剛好症狀相似（收不到通知），所以昨天修完會覺得
「怎麼還是缺」。

---

## 一、根因

### 問題出在 `scripts/live-runner.ts` 的 `notifyIfNeeded()`

這個函式是對**每一個成功執行的 action** 呼叫的（主迴圈 `result.executed`
分支），但函式內部只處理 3 種：

```ts
// 修改前
if (action.kind === 'entry_never_filled')  { ...發推薦單失效...; return; }
if (action.kind === 'update_trailing_stop'){ ...發移動止損...;   return; }
if (action.kind !== 'sync_closed_position') return;   // ← 其餘全部在這裡靜默消失
...發出場通知...
```

最後那行 `return` 就是破口。所有不是這 3 種的 action，執行了、也寫進 DB 了、
清理也做了，**就是不會發通知**。

### 對照表：哪些有、哪些沒有

| 事件 | 對應 action / 路徑 | 修改前 | 修改後 |
|---|---|---|---|
| 新推薦單 | Vercel `route.ts`（不受 live 影響） | ✅ 有 | ✅ 有 |
| 掛單成交 | `notifyFilled`（自我修復偵測） | ✅ 有 | ✅ 有 |
| TP1 達標 | `notifyTp1Hit`（自我修復偵測） | ✅ 有 | ✅ 有 |
| 移動止損上移 | `update_trailing_stop` | ✅ 有 | ✅ 有 |
| 推薦單失效 | `entry_never_filled` | ✅ 有 | ✅ 有 |
| 一般出場（TP/止損） | `sync_closed_position` | ✅ 有 | ✅ 有 |
| **時間止損／盤整停滯／到期平倉** | `close_full_position` | ❌ **沒有** | ✅ **已補** |
| **掛單逾期主動撤單** | `cancel_stale_entry` | ❌ **沒有** | ✅ **已補** |
| **交易對無法下單** | catch 區塊 `symbol_unavailable` | ❌ **沒有** | ✅ **已補** |
| 時間止損的**出場**通知標題 | `sync_closed_position` | ⚠️ **標錯成「止損出場」** | ✅ **已修** |

### 為什麼是這三個被漏掉

三個都是**後來才加進 live-runner 的功能**，加的時候只補了「執行」跟「善後」，
沒有回頭補「通知」：

| action | 何時加入 | 加入時做了什麼 | 漏了什麼 |
|---|---|---|---|
| `cancel_stale_entry` | 2026-08-11 | 撤單 + DB 標記 + 清理鎖 | 通知 |
| `close_full_position` | 時間止損搬進 live-runner 時 | 送 MARKET 單 + 寫 close_reason | 通知 |
| `symbol_unavailable` | 2026-08-09/11 | DB 標記 + 清理鎖 | 通知 |

`notifyIfNeeded` 的原始註解寫著「盤點 route.ts 六個推播點逐一補齊」——
當時補的是**那時候存在的**六個時機，之後新增的 action 沒有人回頭更新它。

### 附帶查到：時間止損的出場通知一直標錯

Vercel 那條路（`route.ts:1169-1172`）**一直都標對**：

```ts
if (closeResult === 'MANUAL_CLOSE' && timeStopFired) pushTitle = `⏱ 時間止損 ${sym}`;
else if (closeResult === 'MANUAL_CLOSE')             pushTitle = `⏱ 到期平倉 ${sym}`;
```

但 live-runner 只用損益正負分兩類：

```ts
const label = action.result === 'WIN_TP1' ? '✅ 出場獲利' : '❌ 止損出場';
```

所以**時間止損關掉且收在負值的單，會被標成「❌ 止損出場」**——使用者看到會
以為是價格碰到止損價。這解釋了為什麼你覺得「只收到止損」：那裡面其實混著
時間止損的單，只是標籤看不出來。

## 二、修改內容

檔案：`scripts/live-runner.ts`

### 1. 補 `cancel_stale_entry` 通知

```
⏱ 掛單逾期取消 SOL/USDT
▲ 做多 掛單超過 4 根 K 線未成交，已主動撤單（未進場，非持倉）
```

跟 `entry_never_filled`（「推薦單失效」）**刻意分開文案**——兩者都是「從未
開倉」，但成因不同：那個是掛單在交易所端自己消失，這個是我們依規格 §3-A
主動撤掉的。

### 2. 補 `close_full_position` 通知（系統主動平倉的那一刻）

```
⏱ 盤整停滯平倉 ADA/USDT
▲ 做多 系統主動平倉中，成交結果稍後回報
```

依 `action.closeReason` 分三種文案：

| closeReason | 推播標題 |
|---|---|
| `time_stop_stall` | ⏱ 盤整停滯平倉 |
| `time_stop_expiry` | ⏱ 到期平倉 |
| `time_stop_expiry_post_tp1` | ⏱ 到期平倉(TP1已達標) |

**這則跟下一輪的出場通知不是重複**：這則說「為什麼關」（立即），下一輪的
`sync_closed_position` 才有實際成交價與損益（MARKET 單的 ACK 不保證帶精確
成交價，要等對帳）。

### 3. 修出場通知的標題（不再把時間止損標成止損）

利用 8/12 已經做好的 `markForceCloseReason`——它會在主動平倉時先把真正的
關單原因寫進 DB，而 `row` 每輪重新查（`select` 已含 `close_reason`），
所以出場通知讀得到那個 pending 值：

```ts
const pending = row.close_reason !== null && PENDING_CLOSE_REASONS.has(row.close_reason)
  ? row.close_reason as TimeStopCloseReason : null;
const label = pending
  ? (CLOSE_REASON_PUSH_LABEL[pending] ?? '⏱ 系統平倉')
  : (action.result === 'WIN_TP1' ? '✅ 出場獲利' : '❌ 止損出場');
```

讀不到才退回原本的損益正負判斷（一般 TP/止損出場行為完全不變）。

### 4. 補 `symbol_unavailable` 通知

```
⚠️ 交易對無法下單 PUMP/USDT
幣安回應 [-4141]，這個交易對目前不可交易，推薦單已取消（未進場）
```

這條路徑在 catch 區塊，獨立於 `executeTradeAction` 之外，之前推薦單就這樣
無聲消失，只有開 App 才看得到卡片變成「交易對目前無法下單」。

⚠️ **誠實說明**：這四種事件都沒有單元測試覆蓋（`notifyIfNeeded` 直接呼叫

真正的驗證只能等實際觸發：
- **時間止損**：持倉卡在 ±0.3R 超過 8 根 K 線 → 應收到「⏱ 盤整停滯平倉」
- **掛單逾期**：掛單超過 4 根 K 線未成交 → 應收到「⏱ 掛單逾期取消」

## 五、為什麼這個 bug 會重複發生（值得記下來）

這是**第三次**因為「加了新功能但沒回頭補通知/環境變數」而收不到推播：

| 次數 | 日期 | 根因 | 層級 |
|---|---|---|---|
| 1 | 2026-08-10 | live-runner 完全沒有推播程式碼 | 功能缺失 |
| 2 | 2026-08-12 | 有程式碼但 VAPID 環境變數沒設 | 傳輸層 |
| 3 | 2026-08-13（本次） | 有金鑰但分派函式漏認 4 種事件 | 分派層 |

**共同模式**：`notifyIfNeeded` 用的是「白名單 + 最後 return」的寫法，
新增 action 時**預設是靜默**，不會有任何提示。

**建議的結構性防呆**（尚未實作，列在這裡供之後決定）：
把 `notifyIfNeeded` 改成 `switch (action.kind)` 並列出**所有** `TradeAction`
的 kind，明確標註哪些是「刻意不發通知」（`place_entry`/`hold`/
`wait_for_fill` 等）。這樣之後 `TradeAction` 聯合型別新增成員時，
TypeScript 的窮盡性檢查（exhaustiveness check）會直接編譯失敗，
逼人回來決定「這個新事件要不要發通知」——而不是像現在這樣默默漏掉。

這個改動不影響行為，純粹是把「漏掉」從執行期靜默錯誤變成編譯期錯誤。
要做的話大約 20 行，但會動到 live-runner 核心通知路徑，建議等這次修的四項
在真實環境驗證過之後再做。
