一旦被觸發就永久解除全部同步監聽器且不再重新註冊。之後只剩手動
「同步紀錄」按鈕還能運作。

## 1. 決定性證據：PriceFeed 活著，StoreHydration 死了

這是整份分析最關鍵的一段。

你回報的兩件事**同時成立**：

- 「明明**打到進場價**」 → 你看得到**即時價格是新的**
- 「紀錄那邊還是寫已達進場等待確認」 → **狀態是舊的**

要顯示「已達進場 等待確認」，程式必須同時滿足
`livePx > 0` 且 `distToEntry <= 0`（[trades/page.tsx:256-259](../src/app/trades/page.tsx#L256)）——
**即時價餵送是正常運作的**。

現在看這兩個元件在 [layout.tsx:38-43](../src/app/layout.tsx#L38) 的位置：

```tsx
<StoreHydration>          {/* 狀態同步 —— 死了 */}
  <PriceFeed />           {/* 價格餵送 —— 活著 */}
  <main>{children}</main>
  <BottomNav />
</StoreHydration>
```

**同一個 root layout、同一個生命週期、導航時都不會卸載。**
兩者都用 `visibilitychange` 在回前景時立刻補一次。唯一的結構差異：

| | PriceFeed | StoreHydration |
|---|---|---|
| effect deps | `[]` | `[userId, hasHydrated]` |
| 閂鎖 | 無 | `syncDoneRef` |
| cleanup 會不會被觸發 | **永遠不會** | **deps 一變就觸發** |
| 觸發後會不會重新註冊 | N/A | **不會**（被閂鎖擋住） |
| 實機結果 | 價格是新的 ✅ | 狀態是舊的 ❌ |

### 這排除了什麼

我原本列的次要假設「iOS standalone PWA 的 `visibilitychange` 不可靠」
**已被推翻**。若那個事件在你手機上不可靠，PriceFeed 也該一起陳舊——
但它沒有。**`visibilitychange` 在你的裝置上確實有在觸發**，
只是 StoreHydration 那個監聽器**已經不在了**。

監聽器會消失的唯一途徑是 effect cleanup。cleanup 跑完卻沒重新註冊的唯一原因
是閂鎖。**這不是推測，是排除法後的唯一解。**

## 2. 根因：單向閂鎖 + cleanup 不對稱

### 2.1 程式碼

[StoreHydration.tsx:739-800](../src/components/StoreHydration.tsx#L739)：

```ts
const syncDoneRef = useRef(false);

useEffect(() => {
  if (!userId || !hasHydrated || syncDoneRef.current) return;   // ← 閂鎖
  syncDoneRef.current = true;                                    // ← 設 true 後永不重置

  loadFromSupabase(userId)...                                    // 初次載入

  const unsub        = useStore.subscribe(...);                  // 4 秒防抖自動存檔
  const periodicSave = setInterval(..., 10 * 60 * 1000);         // 10 分鐘定期存檔
  const periodicSync = setInterval(..., 2  * 60 * 1000);         // 2 分鐘定期同步  ★
  document.addEventListener('visibilitychange', handleVisibility); // 回前景同步   ★

  return () => {                            // ← deps 一變就無條件全部解除
    unsub();
    clearInterval(periodicSave);
    clearInterval(periodicSync);
    document.removeEventListener('visibilitychange', handleVisibility);
    if (saveTimerRef.current) clearTimeout(saveTimerRef.current);
  };
}, [userId, hasHydrated]);
```

**不對稱**：cleanup 無條件解除全部，effect body 卻被閂鎖擋著不會重建。

### 2.2 觸發序列

`userId` 走一趟 `'abc'` → `null` → `'abc'`：

1. 首次執行 → 閂鎖通過 → `syncDoneRef = true` → 四個監聽器註冊
2. `userId` 變 `null` → **cleanup 觸發，四個監聽器全部解除**
   → effect body 重跑，撞 `!userId` 提早 return
3. `userId` 恢復 → effect body 重跑 → 撞 `syncDoneRef.current === true`
   → **提早 return，什麼都沒重建**

結果：定期同步、回前景同步、自動存檔**永久死亡**。
只剩「同步紀錄」按鈕活著——它直接呼叫 `fullSyncFromSupabase()`
（[trades/page.tsx:997](../src/app/trades/page.tsx#L997)），不經過這個 effect。

### 2.3 iOS 為什麼特別容易中，且中了不會自己好

`supabase.ts` 用預設值建 client（[supabase.ts:6](../src/lib/supabase.ts#L6)）：

```ts
export const supabase = createClient(url, key);
// → autoRefreshToken: true, persistSession: true
```

iOS 對背景的 standalone PWA 凍結非常積極。切回前景那一刻：

1. JS 執行緒解凍，supabase-js 立刻嘗試 token refresh
2. **iOS 恢復 App 的速度比恢復網路快** —— refresh 很容易碰上網路還沒好
3. session 出現一瞬間空窗 → `onAuthStateChange` → `setLocalUserId(null)`
   → **cleanup 觸發**
4. 網路恢復、refresh 成功 → `setLocalUserId(uid)` → **閂鎖擋住，不重建**

而你「切到別的 App、沒滑掉」正好是**最糟的組合**：

- 有凍結/解凍 → 足以觸發上面的序列
- 沒有 process 被殺 → `useRef` 不會重置 → **壞掉的狀態一直留著**

如果你每次都滑掉重開，反而不會遇到——因為那會重建整個實例。
**「還在背景運行」正是讓這個 bug 持續存在的條件。**

### 2.4 你的修復儀式，逐步對應

> 「先按同步紀錄，然後把網頁完全關掉再重新進入」

| 步驟 | 實際發生什麼 |
|---|---|
| 按「同步紀錄」 | 唯一還活著的路徑。`fullSyncFromSupabase` → `reconcileFromServer`，把正確狀態寫回 store。zustand persist 中介層會**立刻**寫進 localStorage |
| 關掉重開 | 重建 React 實例 → `useRef` 重置 → 閂鎖解除 → 四個監聽器重新註冊 |
| 分類正常了 | 因為上一步已經把正確資料存進 localStorage，重開後 rehydrate 出來就是對的，不必等網路 |

**兩步都是必要的，不是迷信**：
只按同步不重開 → 監聽器仍然死的，過幾分鐘又壞。
只重開不按同步 → 要等 `loadFromSupabase` 跑完整輪網路往返（watchlist → trades →
profile → `/api/trade-status`），iOS 剛恢復時網路慢，這段期間畫面還是舊的。

## 3. 分項說明

### 3.1 為什麼看起來像「分類按鈕壞了」

按鈕本身沒問題。`setFilter` 是單純的 `useState`
（[trades/page.tsx:549](../src/app/trades/page.tsx#L549)），點了一定更新。

壞的是**底層資料**。分類 chip 是依 `status` 分桶：

```ts
const waiting = useMemo(() => trades.filter(t => t.status === 'waiting'), [trades]);
const pending = useMemo(() => trades.filter(t => !isFinallyClosed(t) && t.status !== 'waiting' && !isUnconfirmedSync(t)), [trades]);
const closed  = useMemo(() => trades.filter(isFinallyClosed), [trades]);
```

`status` 停止更新 → 桶內容是舊的 → 點「持倉中」跳出空的、點「等待進場」
還看到早就成交的單 → 體感就是「按了沒反應」。

### 3.2 為什麼「已達進場 等待確認」會卡住

關鍵限制：**client 讀不到 Supabase 的 `status` 欄位**（authenticated role 無該
column 權限，回 42703）。整條鏈：

1. 伺服器 `route.ts` Phase 1 用 1h K 線判定成交，寫 `status='active'`
2. Client 無法直接讀 → **必須**打 `/api/trade-status`（service role）
3. 那支 API **只**在 `reconcileFromServer()` 裡被呼叫，
   而它只掛在 `loadFromSupabase()` / `fullSyncFromSupabase()` 尾巴

**同步死了 → `reconcileFromServer` 從不執行 → 狀態永遠停在 waiting。**

那句文案字面上是誠實的（本機狀態確實還是 waiting），只是原因不是「等伺服器」，
而是「根本沒去問伺服器」。

#### 次要延遲窗（非本次主因，但修好主因後仍會存在）

**A. 伺服器判定盲窗，最長約 1 小時**（刻意設計）

[route.ts:381-382](../src/app/api/analyze/route.ts#L381)：

```ts
const placedAt    = (trade.opened_at ?? 0) as number;
const evalCandles = candles.filter(c => c.openTime >= placedAt);
```

只採計 openTime ≥ 掛單時間的 1h K 線，但 K 線 openTime 對齊整點：

- 掛單 04:36 → 04:00 那根的 openTime < 04:36 → **被排除**
- 04:50 真的觸價 → 落在被排除的那根裡 → 伺服器看不到
- 要等 05:00 那根才算數

這是**刻意取捨**，註解記錄了真實踩過的坑（不加時間錨的話，掛單前的歷史價格會被
誤判成成交）。**不該為了觀感去動它。**

**B. Client 備援盲窗，最長約 4 小時**

`reconcileIncorrectlyActiveTrades` 用 **4h** K 線卻套同一個時間錨
（[StoreHydration.tsx:447-448](../src/components/StoreHydration.tsx#L447)）：

```ts
const candles     = await fetchCandles(t.symbol, '4h', 500, 2, t.openedAt - 4 * 3600 * 1000);
const evalCandles = candles.filter(c => c.openTime >= t.openedAt);
```

掛單 04:36 → 04:00 排除 → 下一根可用的是 08:00。主路徑失敗時，這個備援
好幾小時都補不上。

### 3.3 已排除的假設

| 假設 | 排除依據 |
|---|---|
| Service Worker 快取舊頁面 | `sw.js` 的 fetch handler 是空 passthrough（`self.addEventListener('fetch', () => {})`），完全沒有快取邏輯 |
| Webhook Secret 錯誤 / 401 | 使用者確認沒看到橘色警告橫幅 |
| iOS `visibilitychange` 不可靠 | **PriceFeed 用同一個事件、同一個 layout 位置，價格是新的** —— 事件有觸發，是監聽器不見了 |
| 桌面捷徑（PWA）本身有 bug | 捷徑不是原因，但它讓實例存活更久、凍結/解凍更頻繁，是觸發並維持這個 bug 的環境 |

## 4. 解決方案

### 修正 A（P0，一次解掉兩個症狀）：讓註冊與 cleanup 對稱

把「只該跑一次的初次載入」和「必須跟著 userId 重建的監聽器」拆成兩個 effect：

```ts
// Effect 1：初次載入 —— 保留 ref 守衛（本來就只想跑一次）
useEffect(() => {
  if (!userId || !hasHydrated || initialLoadRef.current) return;
  initialLoadRef.current = true;
  loadFromSupabase(userId)
    .then(() => pickupServerSignals())
    .then(() => retryPendingDeletes(userId))
    .then(() => retryPendingCoinDeletes(userId))
    .catch(() => {});
}, [userId, hasHydrated]);

// Effect 2：監聽器與計時器 —— 「不要」ref 守衛，跟 cleanup 對稱
useEffect(() => {
  if (!userId || !hasHydrated) return;
  const unsub        = useStore.subscribe(...);
  const periodicSave = setInterval(..., 10 * 60 * 1000);
  const periodicSync = setInterval(..., 2  * 60 * 1000);
  document.addEventListener('visibilitychange', handleVisibility);
  return () => { /* 對稱解除 */ };
}, [userId, hasHydrated]);
```

**最小改動替代方案**：在 cleanup 裡加一行 `syncDoneRef.current = false;`。
副作用是每次重建都會再跑一次初次載入——以本專案的量級可接受，
而且「恢復前景時同步一次」本來就是想要的行為。

### 修正 B（P1）：避免 session 空窗打斷同步

治本一點的做法是讓監聽器不要綁在 `userId` 上。`handleVisibility` 內部本來就
自己讀 `useStore.getState().userId`（[StoreHydration.tsx:782](../src/components/StoreHydration.tsx#L782)），
不依賴 closure 捕捉的值——所以 effect 其實**可以只依賴 `hasHydrated`**，
讓 session 短暫空窗完全不影響監聽器註冊。

這比修正 A 更根本：A 是「壞了會自己重建」，B 是「一開始就不會壞」。
兩者可以一起做。

### 修正 C（P1，讓 §3.2 的延遲窗不再誤導）

即使同步修好，§3.2-A 那個最長 1 小時的伺服器盲窗仍在（那是刻意的設計取捨）。
改文案讓它自己解釋，成本極低：

```
已觸價 · 等待伺服器確認成交（約 1 根 K 線內）· 已等 12 分
```

把「等多久了」顯示出來，使用者就知道系統在正常運作。

### 修正 D（P2）：縮小 client 備援盲窗

`reconcileIncorrectlyActiveTrades` 的 4h K 線改成 1h，與伺服器 Phase 1 一致，
盲窗從約 4 小時降到約 1 小時。

注意：1h 要抓更多根才能覆蓋同樣時間範圍，需一併確認現有 250ms stagger
夠不夠避開 Binance 429。

### 修正 E（P2，效能）

`filtered` 的 useMemo 相依於 `priceOf`
（[trades/page.tsx:847](../src/app/trades/page.tsx#L847)），而 `priceOf` 相依於
整個 `prices` 物件 → PriceFeed 每 3 秒換一次 identity → 整個列表重算並重新排序。

只有 `PROFIT` / `LOSS_LIVE` 兩個模式真的需要即時價，其餘（含最常用的 `ALL`）
完全不用。改成按需訂閱即可。

不是「按了沒反應」的原因，但會讓點擊瞬間感覺遲鈍。

## 6. 修好後的驗收方式

因為這個 bug 依賴 iOS 凍結/解凍時序，自動化測試抓不到，需要實機驗收：

1. 開 PWA，進紀錄頁，確認分類正常
2. 切到別的 App **放置 10 分鐘以上**（要夠久，讓 token 過期、iOS 真的凍結）
3. 切回 PWA，**不要**按同步紀錄、**不要**關掉重開
4. 直接點分類按鈕

**通過條件**：分類立刻正確反映最新狀態。
若還要按同步才對，代表 A/B 沒修乾淨，需回頭再查。

補充：修好後 §3.2-A 那個最長 1 小時的伺服器盲窗仍然存在，
所以「剛觸價的單顯示等待確認」**是正常的**，不算沒修好——
修正 C 的文案就是為了讓這件事一眼可辨。

## 7. 尚未釐清（不影響修法，但值得留意）

`setLocalUserId(null)` 理論上會觸發另一個 effect 把使用者導去 `/login`
（[StoreHydration.tsx:733-736](../src/components/StoreHydration.tsx#L733)）：

```ts
useEffect(() => {
  if (!authReady) return;
  if (!userId && pathname !== '/login') router.replace('/login');
}, [authReady, userId, pathname, router]);
```

但使用者沒回報被踢去登入頁。可能的解釋：空窗極短、`router.replace` 還沒完成
渲染 session 就恢復了。

這不影響修正 A/B 的正確性（監聽器消失是既成事實），但如果修完仍有殘留問題，
這裡是下一個要查的點。
