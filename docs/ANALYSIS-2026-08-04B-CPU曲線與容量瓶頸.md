## 摘要

**最重要的一句話**：出單少的根源不是濾網太嚴，是**容量鏈整條被 CPU 額度綁住**。

```
Vercel CPU 額度 4h/月
      ↓ 逼出
掃描幣種只能 15 個（7/26 從 20 砍下來）
      ↓ 導致
訊號來源少 + 同一批幣反覆撞「持倉鎖定」
      ↓ 加上
總風險上限 ≈ 5 個併發槽位，持倉最長可佔 7 天
      ↓ 結果
近 3 天 1500 候選 → 出單 5
```

放寬品質濾網**解不了這個問題**（A 報告已證明它們都在成本線上）。
真正的槓桿是**CPU 效率**——省下來的額度才能換成更多幣種、更多獨立機會。

| # | 項目 | 類型 | 建議 |
|---|---|---|---|
| B1 | CPU 曲線判讀：目前貼著上限跑，**零餘裕** | 現況 | 需優化才能加幣種 |
| B2 | 訊號計算沒 memoize，15m/1h 每輪重算 3–12 次 | **P1 優化** | 最大的 CPU 槓桿 |
| B3 | 8/4 移動止損修正的 CPU 成本 | 評估 | 極小，不用擔心 |
| B4 | client 端 4h 備援窗口縮到 1h | P1 | A 報告的修正 D |
| B5 | 篩選列表少訂閱即時價 | P2 | A 報告的修正 E |
| B6 | 持倉分類主症狀 | **待你確認** | 比對 build SHA |

### 1.3 7/21–7/25 為什麼掉到 1–2 分？（需要你確認）

這五天的水位只有前後期的 1/5，太劇烈，不像是程式變動造成的
（那段期間的 commit 都是 UI 改版與風控修正，不會讓 CPU 掉 85%）。

**最可能的解釋：那是上一個計費週期的額度用完，函式被限流。**

如果 Vercel 的計費週期不是自然月、而是從註冊日起算（例如每月 25/26 號重置），
時間軸會完美吻合：

- 週期內累積 → 7/19 前後撞到 4h 上限 → 被限流 → 7/21–25 幾乎不執行
- 7/26 新週期重置 → 恢復正常，且因為當天剛好砍成 15 幣，水位變成 ~8 分/天

**請你去 Vercel dashboard 確認計費週期的起訖日**（Usage 頁面通常會顯示
"Resets on ..."）。這件事會直接影響下面的月度推算。

### 1.4 現在還有多少餘裕？答案是幾乎沒有

| 5 分/天 | 155 分 = 2.6h | 安全 |
| 6 分/天 | 186 分 = 3.1h | 尚可 |

## 二、策略：真正的瓶頸不在濾網，在容量

### 2.1 漏斗數據重述（近 3 天，候選 1500 → 出單 5）

| 關卡 | 擋掉 | 佔比 | 類型 |
|---|---|---|---|
| 總風險上限 | 955 | **64%** | 容量 |
| 持倉鎖定 | 372 | **25%** | 容量 |
| 同4H蠟燭 | 66 | 4% | 品質 |
| 分數/組數未達 | 48 | 3% | 品質 |
| BTC逆向 | 32 | 2% | 品質 |
| 多框架未確認 | 22 | 1% | 品質 |

**容量關卡 89%，品質關卡 10%。**

A 報告已經算過：所有品質關卡的影子淨R **除以樣本數**之後，
全都落在來回成本 0.14R 附近（BTC逆向 +0.073R/筆、多框架 +0.13R/筆）。
**放寬它們不會賺錢，只會多繳手續費。**

### 2.2 容量鏈：問題在最上游

「持倉鎖定 25%」的意思是：同一個幣已經有未平倉部位，新訊號直接跳過。
在只監控 15 個幣、而槽位又能被佔到 7 天的情況下，這個數字高得很合理。

真正的因果鏈是：

1. **CPU 額度 4h/月** → 幣種只能 15 個
2. **幣種只有 15 個** → 可選標的少，且同一批幣反覆撞「持倉鎖定」
3. **總風險上限 ≈ 5 個併發槽** → 一次最多 5 筆
4. **持倉最長 168h（7天）** → 槽位周轉慢

要提高出單量，能動的只有這四環。而 **1 是所有問題的上游**。

### 2.3 為什麼不建議直接放寬總風險上限

`MAX_TOTAL_RISK_PCT = 5` 加總的是 `suggested_risk_pct`（ATR 建議值 0.5/1.0/1.5，
平均約 1.0），實際語意是「最多約 5 筆併發」。

放寬到 8 的問題：

- 影子數據只有 **8 筆決勝樣本、+0.18R/筆**，扣掉成本後幾乎歸零，**不足以支撐決定**
- 在你目前 **10% 風險/筆**的設定下，5 筆併發理論上已是 50% 帳戶曝險；放到 8 就是 80%
- 這是**風險偏好問題，不是統計問題**——沒有數據能替你決定

**建議：不動。** 先把上游（CPU → 幣種數）疏通，比在下游硬撐槽位安全得多。

### 2.4 下一個最有價值的量測：槽位周轉率

現在缺的關鍵數字是：**槽位平均被佔用多久？**

- 若多數槽位被「最終只賺 +0.2R 的時間止損單」佔住 24–72 小時，
  那縮短最大持有時間就能直接換到更多出單
- 若槽位周轉本來就快，那瓶頸純粹在幣種數

CSV 裡有 `開倉時間`/`平倉時間`，但**推薦單失效（55%）的那些單不佔槽位**
（它們從未成交），要把它們排除才算得準。

**建議做法**：在漏斗面板加一個「目前 N 個槽位／平均佔用 X 小時」的顯示，
純讀既有資料，不改任何策略邏輯。累積一週後再談要不要縮短持有上限。

## 三、CPU 優化：最大的槓桿在訊號計算，不在 K 線抓取

### 3.1 [B2 · P1] 訊號計算沒 memoize，15m/1h 每輪重算 3–12 次

**這是目前最大、也還沒被碰過的 CPU 熱點。**

現況：`/api/analyze` 每 5 分鐘跑一次，每個幣對 `5m,15m,1h` 三個時框各跑一次
`fetchCandles(symbol, tf, 200)` + `generateSignals()`（內含
`computeIndicators`：EMA20/50/200、RSI、MACD、BB、Donchian、ATR、
結構分析、OB/FVG 掃描…）。

但**訊號只有在該時框收出新 K 線時才會變**：

| 時框 | 新 K 線頻率 | 掃描頻率 | **重複計算倍數** |
|---|---|---|---|
| 5m | 每 5 分 | 每 5 分 | 1×（無浪費） |
| 15m | 每 15 分 | 每 5 分 | **3×** |
| 1h | 每 60 分 | 每 5 分 | **12×** |

也就是說 15m 有 2/3 是白算的、1h 有 11/12 是白算的。

**修法**：比照 `src/lib/regimeCache.ts` 已經驗證過的做法
（4H regime 用 `is4hBarUnchanged` 判定該不該重算），把 per-(symbol, timeframe)
的訊號結果 memoize，key 用最後一根 K 線的 `openTime`：

```ts
// 概念示意，實作時比照 regimeCache.ts 的結構
const cached = getSignalCache(symbol, tf);
if (cached && cached.lastBarOpenTime === candles[candles.length - 1].openTime) {
  signals = cached.signals;          // 這根 K 線還沒收，直接用上次的結果
} else {
  signals = generateSignals(...);
  setSignalCache(symbol, tf, { lastBarOpenTime, signals });
}
```

**為什麼安全**：跟 `regimeCache` 完全同一個論證——輸入（K 線陣列）沒變，
輸出必然相同。這是純 memoize，不是增量遞推，不會有數值漂移風險。

**預期效果**（粗估，需實測驗證）：
若三個時框的計算量相當，理論上限是省下
`(2/3 + 11/12) / 3 ≈ 52%` 的訊號計算量。
即使只實現一半，也足以把 ~7 分/天壓到 5 分以下——**那就有餘裕把幣種加回 18–20**。

**驗證方式**：跟 `186813d` 一樣，部署後比對兩次掃描的 `ScanStatusPanel`
輸出，確認同一根 K 線內 regime/score 完全一致；再隔一天看 Vercel 曲線。

> ⚠️ 誠實提醒：7/28、7/29、7/31 三次 CPU 優化**都沒有實測效果**。
> 這次的差別在於「重複倍數」是可以先算出來的（15m 3×、1h 12×），
> 不是猜的。但**還是要等曲線驗證，不要先當作成功**。

### 3.2 [B3] 8/4 移動止損修正的 CPU 成本：極小，不用擔心

今天 `7e5c541` 加了 `fetchCandlesCached(symbol, '1h', 20)`，每個
Strategy A 未平倉單每輪一次。成本估算：

- 走增量路徑時只抓 **5 根** K 線（`candleCache.ts` 的 `TAIL_BARS`）
- `calcSimpleAtr` 是 14 次迴圈的簡單加總
- `mergeCandles` 是 20 個元素的 slice/concat

以 5 筆未平倉 × 288 次掃描/天計算，多出來的計算量遠低於單一幣種
一次 `computeIndicators`。**相對於 §3.1 的浪費，這個量級可以忽略。**

**曾考慮但否決的做法**：把 Phase 2 的兩次 1h 抓取合併成一次
`fetchCandlesCached(symbol,'1h',168)`，再本地切出 `evalCandles` 與 ATR 窗口。
表面上省一次抓取，但會讓 `evalCandles` 從「只有新 K 線（~2 根）」變成
「成交後全部 K 線（最多 168 根）」，**TP/SL 走訪迴圈的計算量反而暴增**，
而且動到既有的增量設計會帶來正確性風險。**不划算，不做。**

## 四、先前提到但還沒做的事，具體怎麼修

### 4.1 [B4 · P1] client 端成交備援窗口 4h → 1h

**出處**：`BUG-2026-08-03-同步失效與掛單狀態卡住.md` 修正 D

**問題**：`reconcileIncorrectlyActiveTrades`
（[StoreHydration.tsx:447](../src/components/StoreHydration.tsx#L447)）用 **4h** K 線
配上 `openTime >= openedAt` 的時間錨：

```ts
const candles     = await fetchCandles(t.symbol, '4h', 500, 2, t.openedAt - 4 * 3600 * 1000);
const evalCandles = candles.filter(c => c.openTime >= t.openedAt);
```

掛單時間 04:36 → 04:00 那根被排除 → 下一根可用的是 08:00 →
**盲窗最長約 4 小時**。伺服器端用 1h，盲窗約 1 小時，client 備援反而更鈍。

**修法**：改成 1h，與伺服器 Phase 1 對齊。

```ts
// 168 根 1h = 7 天，跟伺服器 Phase 1 的 lookback 一致
const candles     = await fetchCandles(t.symbol, '1h', 168, 2, t.openedAt - 3600 * 1000);
const evalCandles = candles.filter(c => c.openTime >= t.openedAt);
```

**注意事項**：
- 這條路徑**只在 `/api/trade-status` 失敗時才會跑**（主路徑正常時 `suspects` 通常為空），
  所以實際呼叫量不會增加多少
- 既有的 250ms stagger 要保留，避免 Binance 429
- 這是**純 client 端**，不影響 Vercel CPU

### 4.2 [B5 · P2] 篩選列表不必要地訂閱即時價

**出處**：A 報告修正 E

**問題**：`filtered` 的 `useMemo` 相依於 `priceOf`
（[trades/page.tsx:853](../src/app/trades/page.tsx#L853)），而 `priceOf` 相依於
整個 `prices` 物件 → `PriceFeed` 每 3 秒換一次 identity → 整份列表重算並重新排序。

但**只有 `PROFIT` / `LOSS_LIVE` 兩個模式真的需要即時價**，
其餘（含最常用的 `ALL`）完全用不到。

**修法概念**：把需要即時價的分支拆出去，讓一般瀏覽時 `filtered` 不相依於 `prices`。

```ts
// 只有這兩個模式需要即時價，其餘分支不碰 priceOf
const needsLivePrice = filter === 'PROFIT' || filter === 'LOSS_LIVE';
const livePnlSet = useMemo(() => {
  if (!needsLivePrice) return null;
  // 只在這兩個模式下計算，並且把結果收斂成一個 Set<id>
  ...
}, [needsLivePrice, pending, prices]);
```

**優先度低的理由**：7/30 抽出 `TradeRow` + `React.memo`（`7e0a4fa`）已經擋掉
大部分卡片重繪，剩下的只是列表層重排。**體感影響小，不急。**
