# 策略體檢：走向全自動交易前該改什麼

> 日期：2026-08-04
> 資料：`trades-2026-08-04 (2).csv`（118 筆，其中 55 筆有實際損益）
> 狀態：**僅分析，尚未修改任何程式碼**
> 目的：使用者計畫投入全自動交易，先盤點策略面該改什麼

## 先講最重要的一件事

**目前這 55 筆的數據，扣掉交易成本後，還無法在統計上證明策略有正期望值。**

| 指標 | 數值 |
|---|---|
| 平均 R | **+0.320R** |
| 標準誤 | 0.153 |
| 95% 信賴區間 | +0.020R ~ +0.621R |
| **扣成本後（0.14R/筆）平均** | **+0.180R** |
| **扣成本後 95% 信賴區間** | **−0.120R ~ +0.481R** ← **跨越 0** |
| 扣成本後 t 值 | 1.18（要 > 2 才算 95% 顯著） |
| Bootstrap 扣成本後 > 0 的機率 | 88.6% |

**而且高度依賴極值**：

| | n | 平均 R | 扣成本後 |
|---|---|---|---|
| 全部 | 55 | +0.320R | +0.180R |
| **移除最大兩筆贏家**（各 3.50R） | 53 | +0.200R | **+0.060R** |

移掉 2 筆（3.6% 的樣本）就讓扣成本後的優勢從 +0.180R 掉到 +0.060R，
幾乎歸零。這代表**目前的獲利集中在極少數幾筆**，不是穩定分布。

這不是說策略沒用——88.6% 的機率是正的，方向是對的。
但「還沒證明」跟「證明沒有」是兩回事，也跟「可以放大押注」是兩回事。
**這一段是陳述數據，不是建議你該不該做。要不要投入自動交易是你的決定。**

## 第一順位：BTC 混沌區應該「不進場」而不是「降級輕倉」

**這是這份資料裡最大、也最乾淨的單一發現。**

| 分組 | n | 總 R | 平均 R | 扣成本後 |
|---|---|---|---|---|
| 分析依據含「BTC 混沌」（降級 B 級） | 31 | +4.12R | **+0.133R** | **−0.007R** |
| 不含「BTC 混沌」 | 24 | +13.49R | **+0.562R** | **+0.422R** |

差距 **0.43R/筆**。而且排除混沌單後：

- 95% 信賴區間 **+0.082R ~ +1.042R**（不跨 0）
- Bootstrap 扣成本後 > 0 的機率 **96.8%**（vs 全體的 88.6%）

### 這個數據到底在說什麼（重要，別讀錯）

降級只改**倉位大小**（risk 0.5x），**不改 R 倍數**——R 是用進場價與止損距離
算的，跟下多少無關。所以上面的差距**不是降級這個動作造成的**，而是：

> **BTC 混沌期間進的單，本身的 R 表現就顯著較差。**

現行邏輯（`route.ts` v2.1 §1.3）是「混沌不擋，降級成 B 級輕倉」。
但資料顯示這些單扣掉成本後期望值約為 **0**——輕倉只是把一個沒有優勢的
賭注下小一點，不會讓它變成有優勢。

**建議改動**：BTC `regime === 'chaotic'` 時，策略 A 直接**跳過不進場**
（比照現行 `btc_direction` 逆向硬擋的做法），而不是降級。

**風險**：這會再砍掉一部分出單量（31/55 = 56% 的成交單來自混沌期）。
在 CPU/幣種容量已經吃緊的情況下，出單數會更少。這是「品質換數量」的取捨，
需要你決定；但這是目前**唯一一個有統計支撐**的濾網收緊。

### 但這裡有個重要但書

**移動止損今天才剛修好**（commit `7e5c541`）。這 118 筆裡只有 **1 筆**
走過「移動止損（TP1後）」這條路——就是上表的 BANKUSDT，而且**還是回吐了
1.59R**。

也就是說：
- 上面大部分的回吐，是**移動止損還壞著的時候**累積的，不能拿來評估修好後的機制
- 但那唯一 1 筆修好後的樣本，仍然回吐 1.59R（2×ATR 的移動止損對 2.38R 的
  波幅來說可能太寬）

**建議**：先**不要**急著調 ATR 倍數。等移動止損累積 10 筆以上樣本，
再看「修好後」的真實回吐率。現在調等於用壞掉時期的數據去校準新機制。

### 值得重新拿出來討論的：TP1 前的利潤保護

7/21（任務 #4）移除了 TP1 前的利潤階梯，改成「移動止損只在 TP1 後」。
但資料顯示 **時間止損那 12 筆平均只有 +0.034R**，而其中好幾筆 MFE 都到過
1R 以上（AKE 1.47→0.17、BANK 1.20→0.30）。

時間止損影子模擬已證明「砍是對的」（真實 +0.05R vs 不砍 −3.99R），
所以問題不是「該不該砍」，而是「**砍之前那段浮盈沒被保護**」。

**建議**：等移動止損（TP1後）的數據穩定後，再評估要不要恢復 TP1 前的
保本階梯。同樣理由——現在動等於在壞掉的基礎上疊第二層。

## 第三順位（反直覺）：分數越高，表現越差

只看 A 級（排除降級干擾）：

| 得分 | n | 總 R | 平均 R |
|---|---|---|---|
| < 60 | 5 | +3.76R | **+0.752R** |
| 60–64 | 11 | +8.46R | **+0.769R** |
| 65–69 | 6 | +2.82R | +0.470R |
| 70+ | 8 | +3.13R | **+0.391R** |

**分數越高，平均 R 越低**，趨勢單調。

樣本很小（每格 5–11 筆），不能當定論。但這個方向跟 8/1 那份分析的
發現**互相印證**：

> 能拿高分的訊號，靠的正是「趨勢已經很強」的證據（EMA 完美排列、BOS 突破、
> 大時框偏多空 +3）——而那正是行情已經走過一段、進場位置最差的時候。

同一個病根也解釋了「53% 推薦單失效」（63/118）：等訊號條件全部成立時，
價格常常已經跑掉了。

**建議**：**先不要動**。這需要更多樣本才能分辨是真訊號還是雜訊。
但這是下一個值得專門量測的方向——例如記錄「訊號成立當下距離 EMA20 幾個
ATR」，看進場位置的優劣是否能解釋 R 的差異。

## 走向全自動交易前，工程面還缺什麼

以下純粹是系統面的落差盤點，不是要不要做的建議。

### 缺口 1：沒有下單執行層

目前系統**只產生推薦單**，`route.ts` 從頭到尾沒有任何交易所下單程式碼。
自動化需要新增（而且每一項都是能虧錢的地方）：

- 幣安 API 金鑰管理（**這部分我不會經手，也不該經手金鑰值**）
- 下單失敗 / 部分成交 / 拒單的處理
- 滑價保護（限價 vs 市價、可接受偏離）
- **重複下單防護**——目前 Redis 鎖是為了「不重複推播」設計的，
  不是為了「不重複下單」；掛掉重啟時的行為需要重新檢視
- 對帳：交易所實際部位 vs DB 記錄不一致時怎麼辦

### 缺口 2：現有風控是為「推薦」設計的，不是為「自動執行」

| 現有機制 | 自動化下的問題 |
|---|---|
| 熔斷 −3R/日 | 在 10% 風險設定下 = −30% 帳戶才停，對自動化太寬 |
| 同向風險上限 acctRiskPct×2 | 10% 設定下單方向可達 20% 曝險 |
| 總持倉風險評分 5 | 實際語意是「約 4-5 筆」，跟真實帳戶%脫鉤 |
| **最大回撤停機** | **完全沒有** |
| **異常偵測**（連續下單失敗、價格異常） | **完全沒有** |

### 缺口 3：新修好的機制樣本不足

- 移動止損：**1 筆**樣本（今天才修好）
- MFE/MAE：20 筆
- 訊號快取（`ac2376f`）：今天才上，CPU 效果未知

自動化會**放大**任何一個還沒被驗證的行為。

## 建議的優先順序

**現在可以做（有數據支撐）**

1. **BTC 混沌區改成不進場**（而非降級）— 唯一有統計支撐的濾網收緊

**等數據，先別動**

2. 移動止損 ATR 倍數 — 等修好後累積 10+ 筆
3. TP1 前利潤階梯 — 等移動止損穩定後再評估
4. 進場時機/分數關係 — 需要新的量測欄位

**自動化前必須先補（工程面）**

5. 下單執行層 + 重複下單防護 + 對帳
6. 最大回撤停機
7. 風控參數依「自動執行」重新校準（現在的值是為人工推薦設計的）

**建議的驗證節奏**

在投入真錢自動交易前，先讓修好的機制（移動止損、訊號快取）跑 1–2 週，
確認：
- 移動止損真的有在鎖利（看 `移動止損（TP1後）` 出現的頻率與回吐率）
- 扣成本後的期望值信賴區間**不再跨越 0**
- 不再高度依賴極值（移除最大兩筆後仍為正）
