## 問題 1：移動止損從未生效（P0）

### 1.1 你回報的症狀

> 碰到 TP1 會將止損移動，但在等的過程中若碰到移動後的止損卻不會停止，
> 反倒要等到碰到原先的止損才會停止。

**這個描述完全正確，而且比你想的更嚴重——移動止損從來沒有存在過。**

### 1.2 為什麼你「看得到」止損移動

[trades/page.tsx:347](../src/app/trades/page.tsx#L347)：

```ts
const stopLvl = trade.currentStop && trade.currentStop > 0 ? trade.currentStop : trade.entry;
```

`currentStop` 是 null 時，卡片**退回顯示進場價**當作止損位。所以 TP1 後卡片會顯示
「止損已移到進場價、鎖 +0.0R」——看起來像移動止損生效了。

**但伺服器端根本沒有這個止損。** UI 顯示的是一個 fallback 預設值，不是伺服器
真正在執行的保護。兩邊不一致，這就是症狀的來源。

### 1.3 根因：`atr1h` 永遠是 0

[route.ts:628-640](../src/app/api/analyze/route.ts#L628)：

```ts
let atr1h = 0;
if (tradeStrategy === 'A' && candles.length >= 15) {   // ← 這個條件永遠不成立
  ...
  atr1h = trSum / n;
}
```

`candles` 是**增量抓取**的（[route.ts:596-601](../src/app/api/analyze/route.ts#L596)）：

```ts
const rawStart2 = (trade.last_monitored_at ?? trade.filled_at ?? trade.opened_at ?? (now - 168*3600_000));
const startMs   = rawStart2 - 3_600_000;
candles = await fetchCandles(trade.symbol, '1h', 168, 3, startMs);
```

而 [route.ts:892-894](../src/app/api/analyze/route.ts#L892) **每一輪沒關單就寫入
`last_monitored_at = now`**：

```ts
if (!closeResult) {
  await touchMonitoredAt(trade.id as string);   // last_monitored_at = now
  continue;
}
```

外部 cron 每 5 分鐘打一次 → `last_monitored_at` 永遠是 5 分鐘前 →
`startMs ≈ now − 65 分鐘` → `fetchCandles` 帶 `startTime` 給幣安，幣安**只回傳
startTime 之後的 K 線** → **只有約 2 根** → `2 >= 15` 為 **false** →
**`atr1h` 恆為 0**。

（`limit=168` 是上限不是下限，帶了 `startTime` 就只會拿到那之後的根數。）

### 1.4 連鎖後果

`atr1h === 0` 讓四個地方全部被跳過：

| 位置 | 程式碼 | 後果 |
|---|---|---|
| [645](../src/app/api/analyze/route.ts#L645) | `isTp1Hit && ... && atr1h > 0` | 既有 tp1_hit 單的補種被跳過 |
| [701](../src/app/api/analyze/route.ts#L701) / [732](../src/app/api/analyze/route.ts#L732) | TP1 當下初始化 | 移動止損從不建立 |
| [725](../src/app/api/analyze/route.ts#L725) / [752](../src/app/api/analyze/route.ts#L752) | 2×ATR 棘輪 | 從不上移 |

於是 `trailingStop` 永遠是 `0`，導致：

```ts
// route.ts:716（LONG）
if (localTp1Hit && trailingStop > 0 && c.low <= trailingStop) {  // ← trailingStop > 0 恆 false
  closeResult = 'WIN_TP1'; closePrice = trailingStop; break;      //   整段跳過
}
if (c.low <= (trade.stop_loss as number)) {                       // ← 落到這裡
  closeResult = localTp1Hit ? 'WIN_TP1' : 'LOSS';
  closePrice  = trade.stop_loss as number;                        //   以原始止損出場
}
```

**這就是你看到的行為**：碰到移動後的止損不停，一路跌到原始止損才停。

此外 `current_stop` 從沒被寫入 → `/api/trade-status` 回 null → 卡片走 §1.2 的
fallback 顯示進場價 → 造成「有在保護」的錯覺。

### 1.5 資料佐證（三條獨立證據）

**證據 A — 出場價完全等於原始止損**

| 幣種 | 方向 | 進場 | 原始止損 | TP1 | 結果 | 出場價 | R |
|---|---|---|---|---|---|---|---|
| ETHUSDT | LONG | 1904.55 | 1883.61 | 1946.43 | TP1 達標 | **1883.61** | **−1.00** |

程式碼保證 TP1 後地板是進場價（[route.ts:705](../src/app/api/analyze/route.ts#L705)
`Math.max(tp1 − 2×atr, entry)`），最差應該是 **0R**。實際是 **−1.00R**。
單這一筆就吃掉 1R。

**證據 B — MFE 顯示巨額回吐**

| 幣種 | MFE | 實得 R | 回吐 | 出場原因 |
|---|---|---|---|---|
| HYPEUSDT | **3.08R** | **0.32R** | **2.76R** | 到期平倉（TP1已達標） |

價格一度跑到 +3.08R，最後只拿 +0.32R。有正常運作的 2×ATR 棘輪不可能只鎖 0.32R。

**證據 C — 107 筆裡「移動止損出場」出現 0 次**

出場原因分布完全沒有移動止損類別。同期「原始止損」5 次、「到期平倉」3 次。

### 1.7 修法選項

`atr1h` 不能從增量 K 線算。三個選項：

| 選項 | 做法 | 成本 | 評估 |
|---|---|---|---|
| A | ATR 另外抓一次固定 window（`fetchCandles(sym,'1h',30)` 不帶 startTime） | 每筆持倉每輪多一次 API 呼叫 | 簡單但增加 Binance 呼叫與 Vercel CPU |
| B | ATR 存進 DB 新欄位，定期重算 | 要 migration | 較複雜 |
| **C（推薦）** | 改用既有的 `fetchCandlesCached`（`src/lib/candleCache.ts`） | 幾乎為零 | **已有現成基礎設施** |

**推薦 C**，理由：`fetchCandlesCached` 做的正是這件事——保留完整 K 線陣列、
每次只補尾巴。4H regime 已經在用（[route.ts:1853](../src/app/api/analyze/route.ts#L1853)）。
1h 接上去即可，不用新增 API 呼叫、不用 migration。

**額外建議**：`atr1h === 0` 目前是**靜默失效**——沒有 log、沒有 fallback，
所以這個 bug 存活了很久。修的時候應該加上：
- `atr1h === 0` 但 `localTp1Hit === true` 時記 error log
- 或至少讓移動止損有個不依賴 ATR 的保底（例如進場價保本地板），
  這樣即使 ATR 算不出來也不會退回原始止損

### 1.8 回歸測試

抽成純函數 + 單元測試（比照 `monitorMath.ts` 既有做法），至少覆蓋：

1. TP1 後價格觸及移動止損 → 應以 `trailingStop` 出場，**不是**原始 SL
2. TP1 後出場價不低於進場價（LONG）／不高於進場價（SHORT）
3. `atr1h === 0` 時的行為要明確定義，不能靜默退回原始止損
4. 棘輪只上不下

### 1.9 實機驗證：兩個預測全部命中 ✅

根因確認的方式是**先從程式碼推導出兩個可否證的行為預測，再去問使用者**——
如果任一項不符，`atr1h === 0` 的假設就得推翻重查。

| # | 從程式碼推導的預測 | 實機回答 | 結果 |
|---|---|---|---|
| 1 | **從來沒收過**「🛡 移動止損上移」推播 | **沒有** | ✅ 命中 |
| 2 | 卡片止損位**永遠等於進場價**、鎖定 R 永遠 `+0.0R` | **對** | ✅ 命中 |

**預測 1 的推導鏈**：推播需要 `trailingStopUpdated === true`
（[route.ts:762](../src/app/api/analyze/route.ts#L762)）→ 需要 `atr1h > 0` →
若 `atr1h` 恆為 0，這個推播**在任何情況下都不可能發出**。
使用者跑了幾週、有 6 筆 TP1 達標的單，一次都沒收到 → `atr1h` 確實恆為 0。

**預測 2 的推導鏈**：`current_stop` 只在 `trailingStopUpdated === true` 時寫入
（[route.ts:783](../src/app/api/analyze/route.ts#L783) / [811](../src/app/api/analyze/route.ts#L811)）→
恆為 NULL → `/api/trade-status` 回 `currentStop: null` →
卡片走 fallback `? trade.currentStop : trade.entry`
（[trades/page.tsx:347](../src/app/trades/page.tsx#L347)）→ 恆顯示進場價、鎖定 R 恆為 0。

**兩條獨立的推導鏈、兩個獨立的觀察點，全部吻合。**
加上 §1.5 的三條資料佐證（出場價=原始止損、MFE 3.08R→0.32R、
移動止損出場 0 次），根因確認為：

> `candles` 增量抓取導致 `candles.length` 恆約為 2，
> `candles.length >= 15` 恆為 false，`atr1h` 恆為 0，
> 移動止損機制**從未被建立過**。

**不再需要進一步診斷，可直接進入修正。**

## 問題 2：影子模擬說「不要改成市價進場」

### 2.1 螢幕截圖數據

| 取消原因 | 若市價進場模擬淨R | 樣本 |
|---|---|---|
| 直達TP1 | **+3.84R** | 賺 16 虧 0 |
| 行情走遠 | **+2.87R** | 賺 3 虧 0 |
| 逾期未成交 | **−6.13R** | 賺 4 虧 8 |

### 2.2 直覺讀法是錯的

看到「直達TP1 賺16虧0」會想「早該市價進場」。**這是選擇偏誤。**

「直達TP1」這個分類的**定義**就是「價格沒回調、直接衝到 TP1」。影子模擬從
取消當下開始往前走，而那個時間點價格已經在 TP1 附近 → 下一根 K 線幾乎必然
觸及 TP1 → **16 勝 0 敗是分類定義保證的結果，不是策略優勢**。

### 2.3 正確算法：全 population

下單當下你**不知道**這筆會變成哪一類。所以必須三類加總：

```
(+3.84) + (+2.87) + (−6.13) = +0.58R
樣本 16 + 3 + 12 = 31 筆
每筆 ≈ +0.019R
來回成本 ≈ 0.14R/筆
→ 淨約 −0.12R/筆
```

**結論：無條件改成市價進場會虧錢。維持現行「等回調」。**

這正是 8/1 建這個影子模擬的目的——用數據擋下一個看起來很誘人、實際會虧錢的改動。

### 2.4 但確實有一個真問題（暫時無解）

**55%（59/107）的推薦單根本沒成交**，其中 46%（27 筆）是價格朝有利方向跑掉。

這不是「等回調」的錯，比較像**訊號產生時機偏晚**——等訊號條件成立時，行情
已經走完一段。要改的是 `signals.ts` 的進場位選擇邏輯，不是成交方式。

**目前沒有數據能指出該怎麼改，建議先不動。**

## 問題 5：按「持倉」卻列出掛單

### 5.1 症狀

截圖：`持倉 (2)` 為選中狀態，列表卻出現一張 badge 是「等待進場」的 BTC/USDT 掛單。

### 5.2 先確認：那張卡片確實是掛單

三個 UI 元素**只在 `isWaiting` 為真時才渲染**，截圖三個都有：

| 元素 | 位置 | 條件 |
|---|---|---|
| badge「等待進場」 | [page.tsx:235](../src/app/trades/page.tsx#L235) | `isWaiting` |
| 「距進場位 還差 1.06%」 | [page.tsx:260](../src/app/trades/page.tsx#L260) | `isWaiting` |

（[page.tsx:494](../src/app/trades/page.tsx#L494)）**都沒出現**。

→ `trade.status === 'waiting'` 且 `isPending === false`，無疑。

### 5.3 但現行程式碼**不可能**產生這個畫面

兩個分桶在 `status === 'waiting'` 上是嚴格互斥的
（[page.tsx:580](../src/app/trades/page.tsx#L580) / [587](../src/app/trades/page.tsx#L587)）：

```ts
const waiting = trades.filter(t => t.status === 'waiting');
const pending = trades.filter(t => !isFinallyClosed(t) && t.status !== 'waiting' && !isUnconfirmedSync(t));
```

且列表**只有一條渲染路徑**（[page.tsx:1456](../src/app/trades/page.tsx#L1456) `filtered.map(...)`），
沒有另外釘選 waiting 的區塊。

**更關鍵**：截圖上的數字自洽於 `waiting.length === 0`

| chip | 顯示 | 對應程式碼 |
|---|---|---|
| 全部 | 115 | `waiting.length + pending.length + closed.length`（[1335](../src/app/trades/page.tsx#L1335)） |
| 持倉 | 2 | `pending.length` |
| 結束 | 113 | `closed.length` |
| 等待進場 | **無數字** | `waiting.length > 0` 才顯示括號（[1337](../src/app/trades/page.tsx#L1337)） |

`0 + 2 + 113 = 115` ✓ 完全吻合。

> **同一次 render 內，`waiting.length === 0`，卻渲染出 `status === 'waiting'` 的卡片
> —— 在現行程式碼下這是矛盾的。**

已排除的可能：頁面用 `useStore(s => s.trades)` 正常訂閱
（[page.tsx:536](../src/app/trades/page.tsx#L536)）；store 所有更新都建新陣列＋新物件
（`useStore.ts` 全部走 `.map()` 展開），**全專案沒有任何就地變更 `trade.status` 的地方**
（已 grep 確認）。所以不是「memo 沒重算」。

### 5.4 最可能的解釋：瀏覽器在跑舊的 JS bundle

專案自己的程式碼就註記過這個風險（[settings/page.tsx:801](../src/app/settings/page.tsx#L801)）：

> a PWA tab can sit open on a stale bundle for days

近幾天前端改動密集（7/30 抽出 `TradeRow`、8/3 拆 `StoreHydration` 的 effect）。
若這個分頁載入的是舊 bundle，當時的分桶邏輯**可能還沒排除 waiting**。

**驗證方法（30 秒）**：設定頁最下方有 `build xxxxxxx`。
跟目前 `main` 的 commit SHA 前 7 碼比對——**不一樣就是舊 bundle，這題直接結案**
（強制重新整理即可）。

### 5.5 順帶找到兩個**確認的** bug

這兩個跟上面的症狀未必有因果關係，但確實是錯的，該修。

#### Bug A — `sort()` 就地改動被 `useMemo` 快取的陣列

[page.tsx:815-845](../src/app/trades/page.tsx#L815)：

```ts
let base = filter === 'PENDING'   ? pending      // ← 直接拿 memo 陣列的「參考」
         : filter === 'WAITING'   ? waiting      // ← 同上
         : filter === 'CLOSED'    ? closed       // ← 同上
         : ...
base.sort((a, b) => { ... });                    // ← Array.sort 是「就地」排序
```

當 filter 是 `PENDING`/`WAITING`/`CLOSED`，且方向與日期都停在「全部」
（沒有中間的 `.filter()` 產生新陣列）時，`base` **就是 useMemo 快取的那個陣列本身**，
`sort()` 會直接改動它。

後果：
- `pending` / `waiting` / `closed` 的內容順序被外部改掉，但**陣列 identity 沒變**
  → 依賴它們的其他 memo（如 `liveCounts`，[page.tsx:594](../src/app/trades/page.tsx#L594)）
  **不會重算**，用的是被改過順序的資料
- 破壞 `useMemo` 的「快取值不可變」契約，行為變得跟「先前點過哪個篩選」有關

**修法**：`let base = [...pending]`（或其餘分支同理），或改用 `toSorted()`。

#### Bug B — 「全部」的數字漏算 `unconfirmed`

| 位置 | 內容 |
|---|---|
| [1335](../src/app/trades/page.tsx#L1335) 顯示的數字 | `waiting.length + pending.length + closed.length` |
| [820](../src/app/trades/page.tsx#L820) 實際列出的內容 | `[...waiting, ...pending, ...unconfirmed, ...closed]` |

有「同步中」的單時，**全部 chip 的數字會小於實際列出的筆數**。

**修法**：數字加上 `unconfirmed.length`。
