## 1. 已修好的程式碼缺陷

### 1.1 🔴 `status='tp1_hit'` 的單可能以 `result=NULL` 收場 → 虧損冷卻漏擋

**症狀**：DB 裡有 3 筆已平倉的單 `result` 是 NULL
（ENA `trade-1787818337718-1pj58`、BNB `trade-1787788834676-yisaz`、
HYPE `trade-1787689993582-2zwri`，全部是 2026-08-25～08-27 的 trailing_stop 出場）。

**根因**：`status='tp1_hit'` ⇒ `result='WIN_TP1'` 這條不變量由**兩個寫入者**
共同維護，而他們的認知不一致：

| 寫入者 | 標記 TP1 時寫什麼 |
|---|---|
| `route.ts`（DB 模擬） | `status` + `result` + `exit_price` + `pnl_percent` |
| `scripts/live-runner.ts`（真倉） | **只有 `status`** |

而 `route.ts` 關閉一筆 `status='tp1_hit'` 的單時走 `isFinalClosingTp1` 分支，
該分支**刻意不覆寫 `result`**——它假設標記端已經寫過了。兩邊各自都說得通，
交接處 `result` 永遠是 NULL。

**為什麼這件事會痛**（下游全部靜默出錯，沒有任何錯誤訊息）：

- `src/lib/tradeCooldown.ts` 的 `activeCooldowns` 用 `result === 'LOSS'` 判冷卻。
  一筆以 NULL 收場的虧損單**拿不到 24 小時同向鎖定**——剛被證偽的 setup 可以
  立刻再進一次。這是風控漏擋，不只是紀錄難看。
- 勝率、戰績卡、回撤基準都少算這些單。
- 策略B 連兩敗暫停也漏算。

**修法**（`src/lib/tp1Mark.ts`，新檔，唯一定義處）：

- `tp1MarkPayload()` — 標記 TP1 時 `status` 與 `result` 一起寫。
  `live-runner.markTp1Hit` 與 `route.ts` 的 TP1 寫入都改用它。
- `tp1RollbackPayload()` — live-runner 的「反向自我修復」（TP1 條件單還掛著
  ⇒ 一定沒成交 ⇒ 退回 active）現在會連 `result` 一起清掉。不清的話會留下
  一筆「還在跑、卻已經記成 WIN_TP1」的活單。
- `resultOnTp1FinalClose()` — 關單端再補一道：`result` 是空的就回填
  `WIN_TP1`，即使標記端漏寫也不會以 NULL 收場。`route.ts` 三個關單分支
  （主路徑 / `close_reason` 缺欄位 / 最小欄位）全部改用它。

回歸測試：`tests/tp1Mark.test.ts`（7 個）。

⚠ **修改前後的誠實評估**：`route.ts` 現在有 `excludeExchangeManaged`
（`.is('exchange_entry_order_id', null)`），真倉的單不會再被 DB 模擬碰到，
所以這個交接漏洞**目前復發機率低**。這次的修改是把不變量真正釘住（防禦性），
不是在救一個正在漏的洞。那 3 筆是歷史資料。

### 1.2 🔴 策略B 連兩敗暫停被 CANCELLED 與未平倉單擠掉 → fail-open

**根因**：`route.ts` 的 `checkStratBPaused` 原本這樣取「最近兩筆已結束的交易」：

```ts
.not('result', 'is', null)
.order('closed_at', { ascending: false })
.limit(2)
```

兩種「有 `result` 但不是已結束交易」的列會佔位，把真正的連兩敗擠掉：

1. **未平倉的 `tp1_hit` 單**——`result` 已經是 `'WIN_TP1'`、`closed_at` 還是
   NULL。Postgres 的 `ORDER BY ... DESC` 預設 **NULLS FIRST**，這種單會排到
   最前面。
2. **`CANCELLED`**（掛單到期撤銷）——也有 `result`。實測全表 434 筆裡
   **236 筆是 CANCELLED**，佔比高到幾乎必然擠掉真的交易。

兩者都讓這道關卡 fail-open：該暫停的沒暫停，而且完全沒有錯誤訊息。

**修法**：

- SQL 這側加 `.not('closed_at','is',null)` 與 `.neq('result','CANCELLED')`，
  `limit` 放寬到 10 留餘裕。
- 判定抽成純函數 `isStratBPaused(rows, now)`（放在 `src/lib/tradeCooldown.ts`，
  跟 `activeCooldowns` 同一個模式：查詢留在呼叫端、判定放這裡才測得動）。
  它**自己會再過濾一次、自己重排**，不依賴呼叫端有沒有過濾對。

回歸測試：`tests/tradeCooldown.test.ts` 新增 7 個。

### 1.3 🔴 熔斷的連敗計數被 `CANCELLED` 打斷 → fail-open

2026-09-20 執行 §2.2 時順手抓到的第三個洞，跟 1.2 同一族。熔斷 Check 2 是：

```ts
for (const t of rows) { if (t.result === 'LOSS') streak++; else break; }
```

`CANCELLED`（掛單到期撤銷）也有 `result`，於是「虧、撤銷、虧、虧」只算
**1 連敗**而不是 3。撤銷的掛單從來沒有部位，根本不是一個交易結果。
實測全表 436 筆裡 236 筆是 CANCELLED，撞到的機率不低。

**修法**：兩個判準（`dailyWeightedR`、`consecutiveLossStreak`）抽成
`src/lib/circuitBreaker.ts` 的純函數。不是交易結果的列
（CANCELLED、對帳異常）**跳過而不是打斷**——它們既不是一敗，也不構成
「這段連敗結束了」的證據。只有真的獲利才打斷。

回歸測試：`tests/circuitBreaker.test.ts`（12 個）。

### 1.4 🔴 影子模擬的「悲觀軌跡」是捏造的 → 整個調參紀律失去依據

**這是這次體檢裡最嚴重的一個**，詳細根因與修法見 §3 的「✅ 決定與做法」。
一句話版本：`SHADOW_PESSIMISTIC` 2026-08-26 改成預設關閉之後，程式仍然會
寫出 `pessResult`，但那是**複製樂觀結果**來的。於是 `funnel-verdict` 的
「樂觀與悲觀兩端同號才算數」這道把關永遠成立——而這個專案決定「要不要動
某道濾網」靠的就是它。

回歸測試：`tests/shadowSim.test.ts`（9 個）。

### 1.5 🛠 新工具：`npm run audit-invariants`

既有四支診斷工具都在問「DB 跟外部事實對不對得上」，**沒有一支在問「DB 自己
內部一致嗎」**。而上面兩個缺陷都屬於後者——兩個寫入者對同一張表的欄位語意
認知不一致，寫出來的列單看都合理，合起來才矛盾。

`scripts/audit-invariants.ts` 補這個空窗。只讀 Supabase、不打交易所，所以快；
有 🔴 時離開碼 1（可以掛 CI）。目前的 11 項檢查：

| 代號 | 檢查 |
|---|---|
| `CLOSED_NO_RESULT` | 已平倉但 `result` 是 NULL（§1.1 那個 bug 的簽名） |
| `TP1_NO_RESULT` | 標成 `tp1_hit` 但 `result` 還是 NULL 且**還開著**（現在進行式版本） |
| `CLOSED_NO_EXIT_PRICE` | 已平倉（非取消）但沒有出場價 |
| `DUP_OPEN` | 同 symbol 多筆未平倉（幣安是單向持倉，多的那列是幽靈） |
| `BAD_LEVELS` | 止損／止盈在錯誤的一側 |
| `TINY_STOP` | 止損距離 < 0.2%（名目爆炸風險 + 手續費占 R 極高） |
| `STALE_WAITING` | 掛單超過 24h 未成交也未取消 |
| `NAKED_POSITION` | 真倉部位開著但 DB 沒有止損單 id |
| `PNL_MISMATCH` | `pnl_percent` 跟進出場價算不出來 |
| `DUP_ORDER_ID` | 同一張交易所進場單被多列認領 |
| `DIRTY_MARKED` | 已標記對帳異常的單仍在統計範圍內 |

放進 CLAUDE.md 的診斷工具清單時，建議的排序是
**`status` → `audit-invariants` → `audit-exits`**：前兩支都快，第三支要打
幣安 API。

### 2.1 那 3 筆 `result=NULL` 的歷史資料要不要補

程式碼已經修好，不會再產生新的。但既有 3 筆仍然會讓勝率統計少算 3 筆勝單
（全部是正報酬：+4.86% / +1.78% / +3.06%）。

補的話是一句 SQL：

```sql
UPDATE trades SET result = 'WIN_TP1'
WHERE id IN ('trade-1787818337718-1pj58',
             'trade-1787788834676-yisaz',
             'trade-1787689993582-2zwri');
```

**我沒有執行。** 理由：這個專案對「改 DB 損益紀錄」一向很保守

而且其中 HYPE 那筆的 symbol 在對帳報告裡被列為「FIFO 配對最不可靠」之一。
要改的話你點頭我再做。

**✅ 決定與做法（2026-09-20）**：補寫成 `WIN_TP1`，三筆都補。已執行，
只動 `result` 一欄，`pnl_percent` / `exit_price` 原封不動。HYPE 那筆的

要不要讓統計端一律加 `audit_verdict is null or audit_verdict = 'OK'`？
這會改變戰績卡上的數字，所以我沒有自己決定。

### 2.3 兩筆止損距離 < 0.2% 的單

`BTC trade-1788739523052-vca5z` 止損距離 **0.103%**，來回手續費約

`src/lib/feeCost.ts`：

- **止損距離下限的結論沒有被推翻。** 那份測的是「clamp／skip 會不會提升

## 3. 策略層面的發現（不是 bug，是結構）

跑 `scripts/strategy-health.ts` 的結果（真實成交 n=113，90 天）：

```
勝率             26.5%   （30 勝 / 83 敗）
平均賺          1.275R
平均賠         -0.682R
期望值         -0.162R / 筆
損益兩平勝率     34.8%   ← 目前 26.5%，差 8.3 個百分點
```

三個結構性觀察，**都不需要等樣本量就成立**：

1. **毛損益本身就是負的。** 交易所帳：毛已實現 −251.73 USDT，手續費
   −183.30 USDT，資金費率 +14.17，淨 −420.87。成本占淨虧損 46.9%——
   但把成本全部拿掉，毛損益仍然是 −251.73。**所以這不是「手續費吃掉邊際」，
   是「本來就沒有邊際，手續費只是加重」。**

2. **報酬集中在長尾。** 合計 −18.34R；拿掉最好的 3 筆變成 −30.00R
   （那 3 筆貢獻 11.67R）。小樣本下這種形狀不能當成「有邊際」的證據。

3. **顯著性**：全部 113 筆 t=−1.53（不顯著）；但只看對帳判定 OK 的 87 筆
   **每筆 −0.340R、t=−3.31**——那是顯著為負。兩個數字的差距本身就說明
   「髒資料把結論往好的方向拉」。

### 這跟 CLAUDE.md 現有的「不要調參」結論一致

CLAUDE.md 已經記了**七個測死的參數家族**（止損距離下限、S/R 阻力位、
盤整識別、mfeGiveback…）。這次的體檢沒有推翻任何一項，只是補上一句：

> 問題可能不在任何單一參數，而在「進場訊號本身沒有資訊量」。

拒絕漏斗也指向同一件事：過去 7 天候選 1500、**發出 8 筆**（通過率 0.5%），
擋最多的是 `score_gate`（657 筆，44%），而 `score_gate` 的影子判定是
**「悲觀覆蓋 49% 不足，不可用」**——也就是我們連「分數關卡到底擋對沒有」
都還沒有可信的數據。

**這件事我無法靠讀程式碼解決，要跟你討論方向。** 三條路大致是：

| 方向 | 要做什麼 | 風險 |
|---|---|---|
| A. 繼續累積樣本 | 什麼都不改，等 n 夠（偵測 +0.1R/筆 需 n≈680） | 每筆 −0.162R，等的過程在虧 |
| B. 降頻 + 提高單筆品質 | 只做最高信心的 setup，用交易次數換成本 | 樣本累積更慢，驗證更難 |
| C. 重建訊號層 | 承認 v2.1 計分無鑑別力，換一套機制 | 大工程；且 2026-09-03 那次「要不要重建」還沒結論 |

我的看法：**先不要動參數，但可以先做一件零風險的事**——把成本結構做成
每筆單的事前標示（§2.3），因為那是算術，不需要等統計。

### ✅ 決定與做法（2026-09-20）：先補 `score_gate` 的悲觀覆蓋率

選這條的理由：**A/B/C 三條路都需要可信的量測才決定得了，而量測本身是壞的。**

查下去發現根因不是「舊資料沒補」——`shadow_trades` 本來就 14 天 prune，
所以窗口內不可能有 2026-08-22 之前的資料。真正的原因是
`SHADOW_PESSIMISTIC` 於 **2026-08-26 因為 Vercel CPU 超標改成預設關閉**，
而關閉之後 `simulateShadow` **仍然會寫出 `pessResult`**，那些值不是模擬來的：

| 路徑 | 關閉時實際寫出什麼 | 後果 |
|---|---|---|
| 樂觀軌跡結案 | 直接把樂觀結果複製給悲觀 | `netRPess` 恆等於 `netR`，「兩端同號」永遠成立 |
| TIMEOUT | 讀從沒被更新過的 `pessTp1Hit`（恆 false） | 憑空的悲觀，方向跟上面相反 |
| EXPIRED | **完全不寫** pess 欄位 | `pessCovered` 少算，覆蓋率被系統性低估 |

證據就在 2026-09-19 的漏斗報表裡：`circuit_breaker` −7.08 / −7.08、
`btc_direction` −7.00 / −7.00、`confluence` −2.13 / −2.13 **兩端完全同值**。
那不是「結論穩健」，是**根本沒算**。而 `funnel-verdict` 的整套把關規則
（「兩端同號才算數」）就建在這個數字上——也就是說**這個專案用來決定
「要不要動某道濾網」的依據，這一個月來是假的**。

修法（`src/lib/shadowSim.ts`，從 route.ts 抽出來才測得動，9 個測試）：

1. **悲觀軌跡改成預設開啟**（`SHADOW_PESSIMISTIC=0` 才關）。當初關掉的理由
   是 CPU，但它的成本是對**已經抓回來的** K 線陣列多跑一次純比較迴圈
   （96–168 次 `<=`／`>=`），量級是微秒；真正貴的是 `fetchCandles` 的 I/O
   與指標計算，那些兩條軌跡本來就共用。拿微秒級的迴圈換掉整個調參紀律的
   可信度不划算。
2. **關閉時一個字都不寫。** 寧可 `pessCovered = 0`、讓 funnel-verdict 直接
   標「不可用」，也不要寫出看起來很確定的假數字。
3. **EXPIRED 補上 pess 欄位。** 掛單從未成交＝沒有部位，兩條軌跡的 R 都是 0
   （`rFor('EXPIRED')` 回 0），所以這不是「猜一個悲觀值」，是如實記下
   「這筆兩邊一樣」。`score_gate` 覆蓋率只有 49% 主要就是這個原因。
4. **清掉 Redis 裡既有的假值**（`scripts/reset-shadow-pess.ts`，預設試跑）。
   已執行 `--apply`，清了 **75 筆**，只動 `pess*` 四個欄位。
   Vercel 沒有設 `SHADOW_PESSIMISTIC`，所以新的預設值直接生效。

**接下來要等。** 覆蓋率現在是 0，約兩週後重建成真值，屆時再跑
`npm run funnel-verdict`。在那之前**任何濾網都不要動**——包括 `score_gate`。
A/B/C 的選擇留到有可信數字之後再談。
