## 一句話

**工程上還不行。** 不是因為程式寫得不好，是因為**執行層根本還沒接起來**——
`src/engine/` 有 514 行、50 個測試的安全基礎設施，但 grep 全專案，
**沒有任何地方 import 它們**，也沒有任何會下單的 API route。零件齊，機器沒組。

而且更關鍵的是：**現有系統的每一個行為，在交易所上都是不同的實作方式**，
不是「把 K 線判斷換成 API 呼叫」這麼簡單。下面逐條列出。

## 二、`src/engine/` 現況：有什麼、缺什麼

### 已完成（純函數 + 測試，品質不錯）

| 檔案 | 行數 | 內容 | 測試 |
|---|---|---|---|
| `binanceClient.ts` | 183 | HMAC-SHA256 簽名、下單/撤單/查持倉/查槓桿分級 | 8 |
| `preTradeCheck.ts` | 107 | 強平緩衝 3×、保證金上限、最低名目、權益地板、當日虧損 | 15 |
| `killSwitch.ts` | 77 | Redis flag + 自動觸發判斷 | 6 |
| `watchdog.ts` | 75 | 對帳：抓裸倉、孤兒止損單 | 9 |
| `precision.ts` | 72 | stepSize 無條件捨去 / tickSize / minNotional | 12 |

### 三個最致命的缺口

**1. Kill switch 按下去不會平倉。**
`killSwitch.ts` 的註解明講「實際平倉邏輯在 watchdog/runner，不在這裡」。
而 runner 不存在。現在按下 kill switch 只會設一個 Redis flag，
**不會撤任何單、不會平任何倉**。這等於防護的最後一道門是虛的。

**2. 沒有任何地方在用冪等 ID。**
`placeOrder` 有 `newClientOrderId` 參數，註解寫「always set this from the caller」，
但**沒有任何 caller**。這個參數就是防「重試/超時重送導致重複開倉」的唯一機制，
現在完全沒被使用過，也沒被測過。

**3. Vercel 跑不了，但還沒決定跑哪。**
`docs/TODO.md` 已分析過三個理由：沒有靜態出口 IP（API key 綁不了白名單）、
serverless 可能在下單序列中途被殺（**進場成交但止損沒送出 = 裸倉**）、
5 分鐘 cron 粒度太粗（移動止損需要持續改單）。
需要一台 VPS，這個決策還沒做，而它決定後面所有實作。

## 三、要「完全複製現有行為」，逐條缺什麼

這是這份文件的重點。現有系統有 **11 種結局**，每一種在交易所上都要重新實作。

### Phase 1：掛單期（5 種結局）

| # | 現有行為 | 現在怎麼做 | 接交易所要怎麼做 | 缺口 |
|---|---|---|---|---|
| 1 | **成交偵測** | 掃 1h K 線看有沒有觸價 | 交易所直接回報，或 user data stream 推送 | 整段重寫成對帳；**新增部分成交狀態** |
| 2 | **逾期 4 根 K 線撤單** | 比對 `opened_at` 時間差 | `timeInForce: GTD` + `goodTillDate` 丟給交易所自動過期 | `goodTillDate` 最小提前量要 testnet 實測 |
| 3 | **論點失效撤單**（收盤破止損位） | 掃 K 線收盤價 | 必須留在程式裡（動態條件），偵測到後送 DELETE | **撤單與成交的競態處理** |
| 4 | **行情走遠撤單**（自掛單價走 1R） | 掃 K 線收盤價 | 同上 | 同上 |
| 5 | **TP1 直達撤單** | 掃 K 線最高/最低 | 同上 | 同上 |

**#2 是唯一可以丟給交易所做的**，好處是系統掛掉訂單也會自己過期。
#3/#4/#5 是動態條件，必須自己算、自己送撤單。

### Phase 2：持倉期（6 種結局）

| # | 現有行為 | 現在怎麼做 | 接交易所要怎麼做 | 缺口 |
|---|---|---|---|---|
| 6 | **TP1 達標 → 平 50%** | **只改帳面計算，App 內文案已提示手動平倉（`5befa26`，2026-08-06）** | 送 `reduceOnly` 限價/市價單平掉 50% 數量 | **自動下單完全沒實作**（帳目不一致已修，見下方 §四） |
| 7 | **TP2 達標 → 全平** | 掃 K 線 | 掛 `TAKE_PROFIT_MARKET` + `closePosition=true` | 要處理「TP1 平 50% 後剩餘數量」的精度 |
| 8 | **原始止損** | 掃 K 線 | 成交後**立刻**掛 `STOP_MARKET` + `closePosition=true` | 這是 watchdog 要盯的頭號目標 |
| 9 | **移動止損（TP1後）** | 每輪重算 `trailingStop` 寫 DB | **撤舊止損單 + 掛新止損單**（每次移動都要） | 改單期間有空窗；改單失敗要重試；rate limit |
| 10 | **時間止損**（8根K線卡±0.3R） | 掃 K 線算 `progressR` | 自己算，觸發後市價平倉 + 撤止損單 | 平倉與止損單的競態 |
| 11 | **到期平倉**（24/72/168h） | 比對 `filled_at` | 自己算，市價平倉 + 撤所有掛單 | 同上 |

### 移動止損的細節（#9 最複雜）

現有邏輯（`route.ts:711-766`）：

```
初始化：trailingStop = TP1 ∓ 2×ATR，地板 = 進場價（保本）
棘輪：  只朝有利方向移動，從 K 線最高/最低 ∓ 2×ATR 算
```

接交易所後，**每一次棘輪移動都是一次「撤單 + 掛單」**：

- 撤單成功、掛單失敗 → **裸倉**（最危險的狀態）
- 交易所 rate limit 擋下改單 → 止損停在舊位置，但程式以為已經移了
- 改單期間價格剛好打到 → 沒有止損保護

**這一項是整個自動化裡最危險的部分**，因為它是唯一會「主動把既有保護拆掉」的操作。
正確做法是先掛新單、確認成功、再撤舊單（順序反過來會有裸倉窗口），
但這樣中間會有短暫的雙止損單，要處理重複觸發。

## 五、只有接真錢才會遇到的全新狀態

現有系統完全沒有這些概念：

| 狀態 | 現在 | 真實交易所 |
|---|---|---|
| **部分成交** | `isFilled` 是 boolean | 限價單可能只成交 30%。此時送撤單，撤掉的是未成交部分，**已成交的是真實持倉，需要止損不是撤單**。判斷：讀 `executedQty`，>0 就走成交路徑補止損 |
| **撤單/成交競態** | 不存在 | 決定撤單 → DELETE 在路上 → 訂單剛好成交 → 回 `-2011 Unknown order sent`。**不能當成撤單成功**，必須重查 `positionRisk` |
| **滑價** | 止損永遠剛好 −1.00R | MAE 資料顯示實際有 5 筆走過止損價（−1.33 / −1.10 / −1.08 / −1.06 / −1.05R）。真實成交會比紀錄的更糟。**扣成本後平均只有 0.196R，滑價 0.05R 就吃掉四分之一** |
| **手續費** | 用固定 0.14R/筆 估算 | 真實 taker/maker 費率不同、資金費率每 8 小時結算一次、部分平倉會多一次手續費 |
| **交易所拒單** | 不存在 | `-1111`（精度）、`-4164`（最低名目）、`-2019`（保證金不足）、`-1021`（timestamp 過期） |
| **逐倉設定** | 不存在 | Binance **預設全倉**，全倉下一個部位虧損可吃掉整個帳戶。逐倉把最壞情況降級成「賠掉那張的保證金」。symbol 層級設定，**有持倉時改不了** |

## 六、$100 帳戶的實際問題

`preTradeCheck.ts` 的 `MIN_LIQUIDATION_BUFFER_R = 3` 配 $100 本金：

- 幣安期貨最低名目通常 5 USDT（部分幣種 20 USDT）
- 山寨風險折算 0.33 倍後，止損距離寬的訊號算出來的倉位會**低於最低下單額**
- `preTradeCheck` 會擋下來（這是對的），但你會看到**大量「名目不足」的失敗**
- CSV 裡止損距離中位數約 1.1%，但有單到 8%——這類單在 $100 帳戶下幾乎必被擋

**現有 App 已經有這個提示**（`SignalCard` 的「低於交易所最低下單額 5U」），
自動化後會變成大量無聲跳過。要決定：跳過就跳過，還是放大倉位（那就脫離風險模型）。

## 九、誠實的結論

**工程面**：零件品質不錯，但機器沒組。最危險的是「kill switch 按下去不會平倉」
跟「移動止損改單會製造裸倉窗口」——這兩個都不是寫不寫得出來的問題，
是**必須在 testnet 上跑到零誤差才能信任**的問題。

**統計面**：扣成本後 95% 信賴區間仍然跨 0，而且六成優勢來自兩筆單。
這不代表策略沒用，代表**還沒有足夠證據說它有用**。

**我造成的一個問題**：TP1 部分停利只改帳面沒改行為，現在的 R 比實際樂觀。
這一項現在就該修（補推播指示），不用等自動化。

**要不要投入真錢、投多少，是你的決定，這份分析不構成建議。**
如果要往下走，下一步是 §E3：**把 runner 組起來 + 接 testnet**——
testnet 沒有金錢風險，而且是唯一能把上面所有競態問題暴露出來的地方。
